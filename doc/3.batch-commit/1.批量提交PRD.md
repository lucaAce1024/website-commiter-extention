# 批量提交功能 — 产品需求文档（PRD）

## 一、产品背景与目标

在现有「单页 Blog 评论提交」与「导航站一键填充」能力基础上，新增 **批量提交** 能力：从 **飞书文档表格** 读取待提交的外链 URL 清单，经预览与筛选后，**全自动化** 地逐个打开页面、AI 识别填充、提交、验证，并将每条的提交/验证状态 **回写到飞书表格** 对应单元格，形成闭环。

目标用户：需要向大量 Blog 评论站或导航站提交外链的运营/SEO 人员，希望用飞书表格管理待提交列表，并由插件自动执行提交与状态同步。

---

## 二、用户需求归纳（6 步闭环）

| 步骤 | 用户需求描述 | 自动化要求 |
|------|--------------|------------|
| 1 | 从飞书文档的表格中读取「待提交发布」的外链列表清单 | 自动读取：需飞书 API/权限与表格结构约定 |
| 2 | 预览列表，选中当前批次要提交的网站 URL；先筛选「Blog 评论站」类型 | 半自动：展示列表 + 筛选（如按类型）+ 多选/勾选本批次 |
| 3 | 以新 Tab 形式打开每个 URL，等待页面加载完成后，用 AI 识别填充进行自动化提交 | 全自动：顺序/并发策略、等待加载、复用现有 AI 识别与填充逻辑 |
| 4 | 提交完成后等待页面刷新，使用「验证」按钮对当前 URL 进行验证，并记录「检测成功/检测失败」 | 全自动：等待刷新 → 执行验证逻辑 → 记录状态 |
| 5 | 验证完成后回到第 3 步，打开下一个 URL 继续，直到本批次全部完成 | 全自动：循环控制、异常与中断处理 |
| 6 | 在飞书文档中更新对应网站外链的提交状态（定位到单元格并精准更新） | 全自动：按行/列定位单元格，写入状态文案 |

以上 1、3、4、5、6 均希望通过 **自动化** 完成；第 2 步为人工确认批次与筛选，其余为系统自动执行。

---

## 三、实施阶段与顺序（强制顺序）

为实现可测试、可交付的增量，**必须先完成阶段一并通过测试，再进入阶段二**。

| 阶段 | 内容 | 验收标准 |
|------|------|----------|
| **阶段一** | 使用 Side Panel 实现时，将 **Popup 内 Blog 评论页的全部功能完整复刻** 到 Side Panel | 在 Side Panel 中可完成：选站点、看当前页评论表单状态、生成评论并填充、验证本次提交、清除缓存、字段高亮与上下导航等，行为与 Popup 一致；复刻完成后 **先进行测试**，通过后再做阶段二 |
| **阶段二** | 在 Side Panel 已具备完整 Blog 评论能力的基础上，实现 **批量提交**：飞书读表、凭证配置、预览筛选、勾选批次、自动执行、验证、飞书回写 | 能从飞书表格拉取列表、筛选 Blog 评论站、勾选本批次、一键批量执行并回写状态 |

**原则**：复刻 → 测试通过 → 再实现批量提交；不跳过测试。

## 四、Side Panel 中 Blog 评论功能复刻清单

以下为从 Popup「Blog 评论」面板迁移到 Side Panel 时，必须完整复刻的功能与 UI，便于实现时逐项对照。

### 4.1 UI 与交互（与 Popup 一一对应）

| 序号 | 功能/区块 | Popup 对应元素/行为 | 复刻要求 |
|------|------------|---------------------|----------|
| 1 | 当前站点 | 站点下拉框、管理按钮、当前站点 URL 小字、无站点时「添加一个」链接 | 同 Popup；与主设置中的 `currentSiteId` 同步（共用 storage） |
| 2 | 当前页面 | 当前页域名展示（如 `blog.example.com`） | Side Panel 需能获取「当前激活的 Tab」的 URL 并展示域名 |
| 3 | 评论表单状态 | 评论表单：已识别/识别中/失败（含 AI/缓存/关键词）；可填字段数 | 调用 content `getCommentPageState` / `recognizeCommentForm`，展示与 Popup 一致 |
| 4 | 可填字段与导航 | 可填字段数 + 点击行在页面上蓝色虚线框标出可填字段；上/下箭头在字段间跳转 | 支持 `highlightCommentFieldsFromCache`、`highlightCommentFieldPrev`、`highlightCommentFieldNext` |
| 5 | 验证项提示 | 「检测到验证项，将暂停自动提交」提示（橙色） | 当 `hasSpamVerification === true` 时显示 |
| 6 | 无表单提示 | 「未在当前页面检测到评论表单」 | 当无评论表单时显示 |
| 7 | 缓存与清除 | 「当前页已有缓存」提示 +「清除本页评论识别缓存」按钮 | 有缓存时显示提示；清除后刷新表单状态，与 Popup 一致 |
| 8 | 状态消息 | 成功/失败/警告的消息框 + 关闭按钮（在按钮上方） | `showBlogMessage` 等价逻辑，支持 success / warning / error / info |
| 9 | 运行状态栏 | 一行滚动文案：API 耗时、已填充字段数、完整检查结果（如已自动提交/因验证项未提交） | `setBlogStatusLine` 等价逻辑；可与 storage 做 per-URL 持久化以便恢复 |
| 10 | 主操作按钮 | 「生成评论并填充」 | 调用 content `blogCommentGenerateAndFill`，传 title/description/h1、siteId、autoSubmit、llmEnabled、tabId、siteUrl；按钮态：生成中… → 恢复 |
| 11 | 验证按钮 | 「验证本次提交」 | 调用 content `verifyCommentSubmission`，传当前站点 `siteUrl`；展示验证成功/未找到链接 |
| 12 | 快捷操作 | 「Blog 评论站点列表」「设置」 | 打开 options 页对应 tab；可用 `chrome.tabs.create`，不关闭 Side Panel |
| 13 | 其他设置 | 「允许自动提交（慎用）」复选框 | 与 Popup 共用 `settings.autoSubmit`，变更写 storage |

### 4.2 数据与消息流（需在 Side Panel 中实现或复用）

- **获取当前 Tab**：`chrome.tabs.query({ active: true, currentWindow: true })`，用于「当前页面」与所有发往 content 的消息。
- **评论表单状态**：`getCommentPageState`、`recognizeCommentForm(useLlm: false)`，得到 `commentPageState`（hasForm、fieldMappings、recognitionStatus、hasSpamVerification）。
- **生成并填充**：`getPageMetadata` → `blogCommentGenerateAndFill`（含 title、description、h1、siteId、autoSubmit、llmEnabled、tabId、siteUrl）；结果驱动状态栏与消息框。
- **验证**：`verifyCommentSubmission`（siteUrl）；提交后自动验证结果可由 background 在 tab 加载完成后写入 storage，Side Panel 打开时读 `tryShowLastVerifyResult` 等价逻辑并展示。
- **缓存**：`clearCommentMapping`；清除后 `getCommentPageState` + `updateBlogClearCacheState`（读 `blogCommentFieldMappings` 判断当前页是否有缓存）。
- **状态持久化**：与 Popup 一致，按 URL 存 `blog_popup_state_${cacheKey}`（statusLine、statusMessage 文案与类型），Side Panel 打开时恢复。

### 4.3 与 Popup 的差异说明

- **Side Panel 不关闭**：用户切换 Tab 时 Side Panel 仍可保持打开，因此「当前页面」随用户切换的 Tab 变化，需在 Tab 切换或 Side Panel 获得焦点时刷新「当前页面」与评论表单状态。
- **同一套 storage**：站点列表、当前站点、LLM 配置、autoSubmit、blogCommentFieldMappings、blog_popup_state_* 均与 Popup 共用，保证在 Popup 与 Side Panel 之间行为一致。

## 五、功能需求详述（批量提交与飞书）

### 5.1 飞书多维表格：表格结构与字段约定

数据源采用 **飞书多维表格（Bitable）**，表格结构与字段名需与下列约定一致，便于读取与回写。

#### 5.1.1 表格结构（字段名称与用途）

| 列名（中文） | 列名（英文，供配置/兼容） | 字段类型 | 说明 | 读取 | 回写 |
|--------------|---------------------------|----------|------|------|------|
| 外链 URL | url / link_url | 文本 | 待提交的页面完整 URL，必填 | ✅ 必读 | - |
| 类型 | type | 单选/文本 | 取值：Blog 评论站 / 导航站 / 其他；用于筛选 | ✅ 用于筛选 | - |
| 提交状态 | status / submit_status | 文本 | 待提交 / 提交中 / 检测成功 / 检测失败 / 需人工验证 / 超时 / 识别失败 | ✅ 可选展示 | ✅ 精准更新 |
| 最后更新时间 | updated_at / last_updated | 日期时间/文本 | 最后一次状态变更时间，如 2025/12/27 00:21:01 | 可选 | 可选 |
| 备注 | remark / note | 文本 | 人工备注 | 可选 | - |

- **表头**：多维表格第一行为表头，列名需与上表「列名（中文）」或配置的英文列名一致；若使用英文列名，需在插件配置中指定列名映射。
- **行与 URL 一一对应**：回写时通过飞书 **record_id**（列表接口返回）定位行，更新「提交状态」及「最后更新时间」列。
- **类型筛选**：默认或用户选择「先筛选 Blog 评论站」时，仅展示类型为「Blog 评论站」的记录。

#### 5.1.2 读取与回写 API

- **读取**：使用 [飞书多维表格 API](https://open.feishu.cn/document/server-docs/docs/bitable-v1/app-table-record/list)（`GET /open-apis/bitable/v1/apps/:app_token/tables/:table_id/records`），需 `app_token`、`table_id` 及 tenant access token（由 App ID + App Secret 换取）。
- **回写**：使用更新记录接口（`PUT /open-apis/bitable/v1/apps/:app_token/tables/:table_id/records/:record_id`），按 `record_id` 更新「提交状态」与「最后更新时间」字段。

#### 5.1.3 权限与安全

- 需在飞书开放平台创建应用并配置 **多维表格** 相关权限（如 `bitable:app`、`bitable:app_record` 等，以飞书最新文档为准）。
-  tenant access token 由 App ID + App Secret 换取，建议缓存 token 并在过期前刷新；凭证与 token 仅存于 `chrome.storage.local`，不硬编码。

### 5.2 飞书凭证与配置 UI（Side Panel 内必要字段）

在 Side Panel 中需提供 **飞书凭证配置区域**，用于保存多维表格的访问凭证与表格标识，并展示同步状态与最近同步时间。实现时需包含以下 UI 与行为。

#### 5.2.1 飞书凭证（Feishu Credentials）配置项

| 配置项 | 说明 | 输入控件 | 存储 key（建议） |
|--------|------|----------|------------------|
| **App ID** | 飞书开放平台应用的 App ID | 单行文本（可脱敏展示） | `feishu_app_id` |
| **App Secret** | 飞书开放平台应用的 App Secret | 密码框或单行文本（脱敏） | `feishu_app_secret` |
| **App Token** | 飞书多维表格的标识（Bitable 的 app_token，在表格 URL 或设置中获取） | 单行文本 | `feishu_app_token` |
| **Table ID** | 多维表格中的数据表 ID（table_id） | 单行文本 | `feishu_table_id` |

- 以上四项为 **必填**（拉取列表与回写均依赖）；保存前可做非空校验。
- 凭证仅存于 **chrome.storage.local**，不硬编码、不提交到任何远端（除飞书 API 调用所需 token 外）。

#### 5.2.2 同步状态与最近一次同步时间（只读展示）

| 展示项 | 说明 | 示例/取值 |
|--------|------|-----------|
| **同步状态** | 最近一次「从飞书拉取列表」的结果 | **已同步** / 未同步 / 同步失败（可配文案，如「已同步」） |
| **最近一次同步时间** | 上次成功拉取列表的本地时间 | 格式示例：`2025/12/27 00:21:01`（或 `YYYY/MM/DD HH:mm:ss`） |

- 用户点击「从飞书同步」或「拉取列表」并成功后，更新为「已同步」并写入当前时间；失败时更新为「同步失败」，不更新时间。
- 未执行过同步前，可展示「未同步」。

#### 5.2.3 按钮

| 按钮 | 说明 |
|------|------|
| **保存飞书凭证** | 将 App ID、App Secret、App Token、Table ID 写入 storage；可选：保存后自动尝试拉取一次以校验凭证，并更新同步状态与时间 |
| **从飞书同步** / **拉取列表** | 使用已保存的凭证调用飞书 API 拉取表格记录，更新列表数据与「同步状态」「最近一次同步时间」 |

以上为飞书表格读取与配置的细化要求；批量执行、预览筛选、回写等见下文 5.3–5.6。

### 5.3 预览与选中本批次（先筛选 Blog 评论站）

- **预览**：将读取到的表格数据以列表形式展示，列包括：URL、类型、当前状态、备注等；支持分页或虚拟滚动（若条数多）。
- **筛选**：
  - 默认或可选「先筛选 Blog 评论站」：根据表格「类型」列过滤出类型为 Blog 评论的条目；
  - 可扩展：按状态筛选（如仅「待提交」）、按域名分组等。
- **选中**：
  - 用户勾选本批次要执行的 URL（多选）；可提供「全选本页」「全选当前筛选结果」等快捷操作。
- **执行入口**：提供「开始批量提交」按钮，仅对当前选中的条目按顺序执行自动化流程。

### 5.4 新 Tab 打开 URL 与 AI 识别填充

- **打开方式**：每个 URL 使用 **新 Tab** 打开（`chrome.tabs.create`），不在当前 Tab 反复跳转，便于保留进度与排查。
- **等待加载**：
  - Tab 打开后监听 `tabs.onUpdated`，在 `status === 'complete'` 且目标 frame 为 main frame 时视为加载完成；
  - 可配置超时（如 30s），超时则标记该条为「加载超时」并进入下一项。
- **注入与执行**：
  - 在目标 Tab 的页面加载完成后，注入/激活 Content Script，调用现有 **Blog 评论** 或 **导航站** 的识别与填充逻辑（与单页一致）；
  - 若当前 URL 对应类型为「Blog 评论站」，则走 Blog 评论流程：生成评论 → 识别评论表单 → 检测验证项 → 无验证则填充并点击提交；有验证则仅填充并记录「需人工验证」。
  - 若为「导航站」，则走导航站 AI 识别与填充流程（不自动提交或按现有策略）。
- **单条结束条件**：
  - Blog 评论：已点击提交且无验证 或 仅填充并记录需人工；
  - 导航站：填充完成（提交策略与现有一致）。
  - 然后进入「等待刷新 → 验证」环节（仅 Blog 评论需验证本站链接；导航站可跳过或单独定义）。

### 5.5 提交后等待刷新与验证

- **等待刷新**：点击提交后，页面可能整页刷新或局部更新；需等待一段时间（如 3–5 秒）或监听 DOM/URL 变化，再执行验证。
- **验证逻辑**：与现有「验证本次提交」一致：
  - 在当前页面中查找 **指向当前站点档案「网站 URL」** 的可点击链接（`a[href]` 与站点 URL 同源或一致）；
  - 找到 → 记录「检测成功」；未找到或不可点 → 记录「检测失败」。
- **状态记录**：每条 URL 在内存/队列中维护状态：待执行 / 提交中 / 需人工验证 / 检测成功 / 检测失败 / 加载超时 / 识别失败 等，供进度展示与飞书回写。

### 5.6 循环至本批次完成

- **顺序**：按用户勾选顺序（或表格行序）依次处理；当前条完成（含验证或超时/失败）后，关闭或保留当前 Tab（可配置），再打开下一个 URL。
- **节奏控制**：可配置间隔（如每站间隔 5 秒），避免请求过于集中。
- **异常与中断**：
  - 单条失败不阻塞后续：记录该条状态后继续下一条；
  - 用户可随时「暂停/停止」批量任务；暂停时当前条可执行完再停，或立即停（需定义）。
- **完成**：本批次全部执行完毕后，汇总统计（成功数、失败数、需人工数），并触发飞书回写。

### 5.7 飞书文档中更新提交状态（精准更新单元格）

- **回写内容**：将每条 URL 的最终状态写入飞书表格的「提交状态」列（及可选「最后更新时间」列）。
- **定位方式**：根据「行」定位到对应单元格：
  - 行：与读取时的行序或唯一键（如 URL）对应，确保更新的是同一行；
  - 列：按约定的「提交状态」列名或列索引写入。
- **API**：使用飞书文档/多维表格的「更新单元格」或「更新记录」类 API，传入 document/table 标识 + 行索引（或 record_id）+ 列标识 + 新值。
- **幂等与重试**：网络失败时可重试；避免同一行重复写入冲突（以最后一次状态为准）。

## 六、Popup 与 Side Panel 承载能力评估

### 6.1 现有结论（引用《Popup 失焦与状态保持需求可行性评估报告》）

- **Popup 失焦即关闭**：Chrome 扩展 Popup 在失去焦点（点击页面、切换标签页等）时会自动关闭，**无官方 API 可禁止**，属于平台限制。
- **状态持久化**：已实现按 URL 的状态持久化与恢复，因此「再打开 Popup 时状态不消失」可行；但 **Popup 关闭期间，若自动化逻辑依赖 Popup 的 JS 上下文，则会被销毁**。
- **长时间自动化**：批量提交是 **长时间、多步骤** 的流程（读飞书 → 多次开 Tab → 填充 → 验证 → 回写），若由 Popup 内的脚本主导：
  - 用户一旦点击其他区域或切换 Tab，Popup 关闭，**主导批量流程的脚本上下文随之销毁**，定时器、Promise 链、循环都会中断，**无法可靠地「在后台」跑完整个批次**。
  - 因此，**仅靠当前 Popup 形态无法可靠支撑「全自动批量提交」**。

### 6.2 推荐方案：Background + Side Panel（或独立窗口）

| 方案 | 说明 | 对批量提交的适用性 |
|------|------|---------------------|
| **Popup 主导** | 由 Popup 脚本顺序调用 chrome.tabs / messaging | ❌ 失焦即关闭，流程中断，不适合 |
| **Background 主导 + Popup 仅做触发与展示** | 批量逻辑放在 Service Worker（background），Popup 只发「开始/暂停」并轮询或监听消息展示进度 | ⚠️ 可行但体验差：用户看不到持久化进度界面（Popup 一关就没了），只能再次打开 Popup 看状态；且 Service Worker 可能休眠，需用 Alarms 或 keep-alive 策略 |
| **Background 主导 + Side Panel 做控制与进度** | 批量逻辑在 Background；**Side Panel** 作为常驻控制面：启动/暂停、列表预览、筛选、勾选、实时进度与状态列表、飞书回写结果 | ✅ **推荐**：Side Panel 在切换 Tab 时不会关闭，用户可随时查看进度；Background 负责开 Tab、消息调度、飞书读写，不依赖 Popup 生命周期 |
| **独立窗口 (Panel/Window)** | 用 `chrome.windows.create()` 打开小窗口，内嵌与 Popup 类似的 UI | ✅ 可行：同样不因点击页面而关闭，但需用户主动关闭窗口；与 Side Panel 二选一即可 |

### 6.3 结论与建议

- **当前 Popup 无法可靠支撑「全自动批量提交」**：一旦失焦关闭，主导流程的脚本即销毁，自动化会中断。
- **建议新增 Side Panel**（Chrome 114+，MV3 已支持）：
  - 用于：飞书表格拉取与展示、预览、筛选（先筛 Blog 评论站）、勾选本批次、启动/暂停批量、实时进度与每条状态、飞书回写结果展示。
  - 批量执行逻辑放在 **Background**：由 Side Panel 发消息启动任务，Background 顺序执行「开 Tab → 注入与填充 → 等待与验证 → 回写状态」，并向 Side Panel 推送进度（或 Side Panel 轮询 Storage/消息）。
- **方案 A：用 Side Panel 替代 Popup**  
  用户点击工具栏扩展图标时，**直接打开 Side Panel，不再弹出 Popup**。实现要点：
  - **Manifest**：移除 `action.default_popup`，新增 `side_panel.default_path`（如 `sidepanel/sidepanel.html`）。
  - **Background**：监听 `chrome.action.onClicked`，调用 `chrome.sidePanel.open({ windowId })` 打开 Side Panel。
  - 导航站、Blog 评论、批量提交等所有功能均迁入 Side Panel，统一入口。

## 七、数据流与状态机（简要）

1. **拉取**：飞书 API → 表格行数组 → 展示在 Side Panel。
2. **筛选与勾选**：按类型筛选（如 Blog 评论站）→ 用户勾选本批次 → 生成「本批次 URL 列表」。
3. **执行**：Background 按序对每个 URL：开 Tab → 加载完成 → 填充（+ 提交）→ 等待刷新 → 验证 → 记录状态 → 下一项。
4. **回写**：本批次全部结束后（或每完成一条即回写），按行更新飞书表格「提交状态」列（及可选「最后更新时间」）。

状态枚举建议：`pending` | `running` | `need_manual` | `verify_success` | `verify_fail` | `timeout` | `error`。

## 八、非功能需求

- **权限**：需申请飞书应用并配置文档/表格读写权限；插件侧需 `storage`、`scripting`、`tabs`、可选 `alarms`（若用 Alarms 保活 Background）。
- **安全**：飞书 Token 不硬编码；敏感配置存 `chrome.storage.local`。
- **性能**：单条超时、整批超时可配置；间隔与并发数（若未来支持并发）需可控，避免对目标站造成压力。
- **兼容**：Side Panel 需 Chrome 114+；飞书 API 以当前开放平台文档为准。

## 十、测试与验收建议

**阶段一（Blog 复刻）**

1. **Side Panel 打开与当前 Tab**：打开 Side Panel，切换浏览器 Tab，确认 Side Panel 不关闭；当前页面域名随激活 Tab 变化。
2. **Blog 评论全流程**：在 Side Panel 内选择站点，打开一页 Blog 评论页，执行「生成评论并填充」→ 检查状态栏与消息 → 执行「验证本次提交」；与 Popup 同页操作结果一致。
3. **缓存与清除**：有缓存时显示「当前页已有缓存」与可填字段数；清除缓存后状态更新；可填字段高亮与上/下箭头跳转正常。
4. **状态持久化**：执行到一半后切换 Tab 再切回，或关闭 Side Panel 再打开，运行状态与结果消息能恢复（与 Popup 的 per-URL 状态一致）。

**阶段二（批量与飞书）**

5. **飞书凭证与同步**：填写 App ID、App Secret、App Token、Table ID，点击「保存飞书凭证」→「从飞书同步」；同步状态为「已同步」，最近一次同步时间更新为当前时间（如 2025/12/27 00:21:01）；列表展示与表格一致。
6. **飞书表格结构**：测试表含 5.1 节约定列（外链 URL、类型、提交状态、最后更新时间、备注）；读取与回写列名/record_id 正确。
7. **批量流程**：勾选 2–3 条 Blog 评论 URL，执行批量；顺序、等待、验证结果与飞书回写一致；中途切换 Tab 不中断（Background 主导）。
8. **异常**：单条超时、单条验证失败、用户暂停，状态与飞书回写正确。
