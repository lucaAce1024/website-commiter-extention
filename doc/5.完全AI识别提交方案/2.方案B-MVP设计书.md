# 方案 B：完全 AI 识别提交 — MVP 设计书

**当前实现已收敛为「程序主控」**：AI 仅生成评论，定位与执行由程序完成。详见 [6.收敛方案-程序主控](./6.收敛方案-程序主控.md)。

## 一、文档说明与 MVP 原则

- **目标**：在 website-commiter-extention 内自建「轻量 Agent」，不依赖 AIPex 运行时，实现「整页 Snapshot + UID 操作 + 多轮弹窗/程序执行」，解决弹窗、无常规提交按钮、仅 comment+link 等问题。
- **MVP 原则**：先做**最小可验证闭环**（设计 → 实现 → 验证 → 迭代），确保「单页：取 snapshot → LLM 决策 → 按 uid 执行 → 多轮至完成/超时」跑通，再扩展与批量/飞书对接。
- **重要约束**：AIPex 依赖本地运行 MCP Server（如技能、干预等能力通过 MCP 暴露）；本方案**不依赖任何 MCP**，全部逻辑在扩展内（Background + Content Script）完成，无需额外进程或本地服务，便于在任意环境一键加载扩展即用。

---

## 二、约束与边界

| 约束项 | 说明 |
|--------|------|
| **无 MCP 依赖** | 不调用 AIPex 的 MCP、不启动本地 MCP Server。Snapshot 采集、格式化、UID 解析与执行、多轮循环、LLM 调用均在扩展内完成。 |
| **运行环境** | Chrome Extension MV3：Background (Service Worker) + Content Script。LLM 请求由 Background 发起（复用现有 API 配置）。 |
| **单 Tab 单任务** | MVP 阶段仅支持「当前指定 Tab 内」完成一条评论提交任务；批量列表与飞书回写沿用现有流程，仅将「单条执行体」从 formHandler 换成本方案。 |
| **不引入 AIPex 包** | 不 npm 依赖 `@aipexstudio/dom-snapshot` 等；参考其思路，在项目内用原生 JS 实现 Snapshot 与执行层，避免构建/依赖复杂度。 |

## 三、系统架构（MVP）

```
┌─────────────────────────────────────────────────────────────────────────┐
│  Side Panel / Background（批量入口）                                       │
│  - 触发「完全 AI 识别」单条任务（tabId, siteUrl, generatedComment）          │
│  - 多轮调度：取 Snapshot → 调 LLM → 解析操作序列 → 下发执行 → 判断终止/继续   │
└─────────────────────────────────────────────────────────────────────────┘
                    │                              │
                    ▼                              ▼
┌──────────────────────────────────┐  ┌──────────────────────────────────┐
│  Background                       │  │  Content Script (目标 Tab)        │
│  - 向 Content 请求 Snapshot        │  │  - 采集 DOM Snapshot（含 UID）    │
│  - 调用现有 LLM 接口               │  │  - 响应 executeAction(uid, ...)    │
│  - 解析 LLM 返回的操作列表         │  │  - 通过 data-wce-nodeid 解析 UID   │
│  - 向 Content 下发操作并收集结果    │  │  - 执行 click / fill              │
│  - 多轮终止判断与超时控制          │  │  - 不依赖 CDP / debugger          │
└──────────────────────────────────┘  └──────────────────────────────────┘
```

- **Snapshot 采集**：仅在 Content Script 中执行（可访问目标 Tab 的 document）。
- **LLM 调用**：仅在 Background 中执行（复用现有 GLM/API 配置）。
- **操作执行**：由 Background 通过 `chrome.tabs.sendMessage(tabId, { action: 'fullAiExecute', payload })` 或 `chrome.scripting.executeScript` 在目标 Tab 内执行；执行层仅根据 UID 查找 DOM 并 click/fill，不依赖 MCP 或 CDP。

## 四、Snapshot 实现规格

### 4.1 职责与执行位置

- **谁执行**：Content Script（已注入到目标 Tab 的页面）。
- **何时执行**：Background 发送消息 `fullAiTakeSnapshot`，Content 在目标 Tab 内同步或异步返回结果。
- **不依赖**：不依赖 Chrome DevTools Protocol、不依赖 debugger、不依赖任何外部 MCP；仅使用 DOM API 与扩展消息。

### 4.2 UID 的生成与持久化

- **属性名**：使用 `data-wce-nodeid`（与 AIPex 的 `data-aipex-nodeid` 区分，避免与其它扩展冲突）。
- **生成规则**：在**首次遍历 DOM 时**对需要参与 Snapshot 的每个可交互/可见节点：
  - 若该元素已有 `data-wce-nodeid`，则复用；
  - 否则生成唯一 ID，建议格式：`wce-${tabId}-${shortUuid}` 或 `wce-${Date.now().toString(36)}-${counter}`，并调用 `element.setAttribute('data-wce-nodeid', uid)` 写入 DOM。
- **作用域与稳定性**：同一轮 Snapshot 内，同一 DOM 节点对应唯一 UID；多轮之间若 DOM 未重排（如仅关弹窗、未整页刷新），则 UID 保持不变，便于后续执行时通过 `document.querySelector('[data-wce-nodeid="' + cssEscape(uid) + '"]')` 精确定位。若页面发生整页刷新，则需重新取 Snapshot，旧 UID 失效。

### 4.3 采集范围（与 AIPex 对齐）

- **包含**：可交互元素（`button`、`input`、`textarea`、`select`、`a[href]`、带 `role="button"` 或 `cursor:pointer` 的 div 等）、以及有意义的文本节点（用于 LLM 理解「Accept」「Comment」「Submit」等文案）。
- **排除**：`script`、`style`、`hidden`、`display:none`、`visibility:hidden`、常见蜜罐类（如 `aria-hidden="true"` 的输入框）。
- **可选**：对 iframe 仅当同源时可递归采集；MVP 可先不递归 iframe，仅主文档。

### 4.4 Snapshot 数据结构（内存侧）

Content 侧维护或返回一个可序列化结构，例如：

```ts
interface SnapshotNode {
  id: string;           // UID，与 data-wce-nodeid 一致
  role: string;         // 如 "button" | "textbox" | "link" | "StaticText"
  name?: string;        // 可访问名称、placeholder、或文本内容
  value?: string;       // 当前 value（input/textarea）
  children: SnapshotNode[];
  tagName?: string;     // 如 "button", "input"
  disabled?: boolean;
  // 其它可选：placeholder, href 等
}
interface SnapshotResult {
  root: SnapshotNode;
  idToNode: Record<string, SnapshotNode>;  // uid -> node，便于执行时校验
  totalNodes: number;
  url: string;
  title: string;
}
```

### 4.5 Snapshot 文本格式化（发给 LLM）

- **目的**：将树结构转成**单行一节点**的纯文本，带缩进表示层级，便于 LLM 理解并输出「对哪个 uid 做何种操作」。
- **格式约定**（与 AIPex 的 formatNode 思路一致，便于 prompt 稳定）：

每行格式示例：

```
[depth] uid=xxx role "name" <tagName> [value="..."][disabled][...]
```

- **depth**：空格缩进（如 2 空格一级），表示父子关系。
- **uid**：仅对可操作节点输出（StaticText 可不带 uid，因不可点击/填写）。
- **role**：button / link / textbox / combobox / checkbox / radio / StaticText 等。
- **name**：按钮文案、输入框 placeholder、链接文本、静态文本内容等，引号包裹。
- **tagName**：可选，`<input>`、`<button>` 等，辅助模型区分类型。
- **value**：当前输入框/textarea 的值，可选。
- **disabled** 等布尔：可选，便于模型判断是否可点。

示例片段：

```
  uid=wce-abc123 button "Accept" <button>
  uid=wce-def456 link "Privacy policy" <a>
    uid=wce-ghi789 textbox "Comment" <textarea> placeholder="Write your comment..."
    uid=wce-jkl012 button "Post Comment" <button>
```

- **长度控制**：对 `name`/`value` 做最大长度截断（如 160 字符），总 Snapshot 文本可设上限（如 12k 字符），超出则从叶子开始裁剪或只保留前 N 个可交互节点，避免 token 超限。

### 4.6 实现要点小结

| 项目 | 说明 |
|------|------|
| 执行位置 | Content Script（目标 Tab） |
| UID 存储 | `data-wce-nodeid`，遍历时按需生成并写入 DOM |
| 遍历方式 | 递归 DOM（document.body），按节点类型/可见性/角色过滤 |
| 输出 | 内存结构 SnapshotResult + 格式化为字符串 snapshotText 供 Background 发给 LLM |
| 无 MCP | 全部在扩展内，不调外部服务（除既有 LLM API） |

## 五、UID 解析与执行实现规格

### 5.1 执行位置与方式

- **执行位置**：必须在**目标 Tab 的页面上下文**内执行，因为只有该上下文能访问当前 DOM 与 `data-wce-nodeid`。
- **两种实现方式二选一**（MVP 任选其一）：  
  - **方式 A**：Content Script 监听消息，收到 `fullAiExecute` 时在 Content 内根据 uid 查找元素并执行 click/fill（Content 与页面共享 DOM，可访问已设置的 `data-wce-nodeid`）。  
  - **方式 B**：Background 使用 `chrome.scripting.executeScript` 向目标 Tab 注入一段函数，该函数接收 `{ action, uid, value? }`，在页面内 `querySelector` 查 uid 并执行。  
- **推荐 MVP**：方式 A（Content 消息），实现简单、与现有 content 架构一致；若遇「Content 未注入」的极端情况，可再考虑方式 B 的注入重试。

### 5.2 查找元素（UID 解析）

- **选择器**：`document.querySelector('[data-wce-nodeid="' + cssEscape(uid) + '"]')`。  
- **cssEscape**：对 uid 中可能存在的特殊字符（如 `"`、`\`）进行转义，可用 `CSS.escape(uid)`（若环境支持）或自定义转义。  
- **同页 iframe**：若 Snapshot 将来包含同源 iframe 内节点，则执行时需在对应 iframe 的 document 中查找；MVP 可仅主文档。  
- **未找到**：返回明确错误（如 `element_not_found`），由 Background 决定是否重取 Snapshot 或结束本轮。

### 5.3 支持的操作类型（MVP）

| 操作 | 参数 | 行为 |
|------|------|------|
| **click** | uid | 对元素执行 `element.click()`，可选先 `scrollIntoView`、再 `dispatchEvent` 模拟点击，以提高兼容性。 |
| **fill** | uid, value | 对 input/textarea 设置 `element.value = value`，并触发 `input`/`change` 等事件，以便 React/Vue 等框架响应。 |

- **可选扩展**：hover、checkbox 勾选等可在迭代阶段加入；MVP 仅 click + fill 即可覆盖「关弹窗 + 填评论 + 点提交」。

### 5.4 消息协议（Content 侧）

- **取 Snapshot**  
  - 请求：`{ action: 'fullAiTakeSnapshot' }`（由 Background 发往目标 Tab 的 Content）。  
  - 响应：`{ success: true, snapshotText: string, snapshotResult: SnapshotResult }` 或 `{ success: false, error: string }`。  

- **执行操作**  
  - 请求：`{ action: 'fullAiExecute', steps: [ { op: 'click', uid: string } | { op: 'fill', uid: string, value: string } ] }`。  
  - 响应：`{ success: boolean, results: [ { op, uid, ok: boolean, error?: string } ], message?: string }`。  

- 所有通信均通过 `chrome.runtime.sendMessage` / `chrome.tabs.sendMessage`，不经过 MCP。

### 5.5 实现要点小结

| 项目 | 说明 |
|------|------|
| 解析 | 通过 `data-wce-nodeid` 在目标 Tab 的 document 中 querySelector |
| 执行 | Content 消息处理函数内执行 click/fill，或 scripting.executeScript 注入函数 |
| 安全 | 仅执行 LLM 返回的 op+uid+value，不执行任意代码；value 仅作字符串填入，不做 eval |
| 无 MCP | 不依赖任何 MCP 或 CDP |

## 六、多轮终止条件与超时（精确描述）

### 6.1 单轮流程

1. Background 向目标 Tab 的 Content 发送 `fullAiTakeSnapshot`，获取当前页的 `snapshotText`。  
2. Background 将 `snapshotText` + 任务描述 + 当前轮次/历史摘要（可选）组装为 prompt，调用现有 LLM 接口。  
3. LLM 返回**本轮操作**（或「无操作 + 结束」）。约定返回格式见下节。  
4. Background 解析返回，向 Content 发送 `fullAiExecute`，执行本轮的 click/fill 列表。  
5. 根据**终止条件**判断：若未终止，则等待短暂间隔（如 800ms～1.5s）后回到步骤 1，开始下一轮；若终止或超时，则结束任务。

### 6.2 终止条件（满足其一即终止）

| 条件 | 说明 |
|------|------|
| **LLM 显式结束** | LLM 返回中带有 `done: true` 或等价字段，表示「任务已完成，无需进一步操作」。 |
| **达到最大轮数** | 已执行轮数 ≥ `MAX_TURNS`（建议 MVP 取 10）。防止死循环。 |
| **单轮超时** | 单轮总耗时（取 Snapshot + LLM 调用 + 执行）超过 `ROUND_TIMEOUT_MS`（建议 25s），则本轮视为失败并终止任务。 |
| **总任务超时** | 从任务开始到当前的总耗时超过 `TASK_TIMEOUT_MS`（建议 90s），立即终止。 |
| **执行错误且不可重试** | 若本轮执行返回 `success: false` 且错误为 `element_not_found`，可配置为「重试一次（重取 Snapshot）」或直接终止；MVP 可简化为「一次 element_not_found 即终止」。 |

### 6.3 超时实现方式

- **单轮超时**：Background 用 `Promise.race([ roundWork(), timeout(ROUND_TIMEOUT_MS) ])`，超时则拒绝并进入终止逻辑。  
- **总任务超时**：在任务入口记录 `startTime`，每轮开始前检查 `Date.now() - startTime > TASK_TIMEOUT_MS`，若已超则不再发起下一轮并返回「任务超时」。  
- **不依赖 MCP**：所有计时与中断均在 Background 的 JS 中完成，无需外部进程或 MCP。

### 6.4 参数建议（MVP）

| 参数 | 建议值 | 说明 |
|------|--------|------|
| MAX_TURNS | 10 | 最大轮数 |
| ROUND_TIMEOUT_MS | 25000 | 单轮 25s |
| TASK_TIMEOUT_MS | 90000 | 总任务 90s |
| INTER_TURN_DELAY_MS | 1000 | 轮间间隔 1s，便于页面稳定 |

## 七、LLM 请求与响应约定（MVP）

### 7.1 请求（Background 构造）

- **系统/角色**：固定说明「你是页面自动化助手，根据当前页面 Snapshot 输出下一步操作；仅输出给定 JSON，不要其他解释。」  
- **用户/内容**：  
  - 任务描述（固定模板 + 变量），例如：  
    - 「任务：1）如存在 Cookie/隐私同意弹窗，先点击接受/同意类按钮关闭；2）找到评论输入框，填入以下内容（必须包含链接）：`${generatedComment}`，链接为：`${siteUrl}`；3）找到并点击提交/发布按钮。若某步无法完成则返回 done 并说明。」  
  - 当前轮次：`round: k / MAX_TURNS`。  
  - 当前 Snapshot 文本：`snapshotText`（截断后）。  

- **变量**：`siteUrl`、`generatedComment` 由调用方（批量逻辑或 Side Panel）传入。

### 7.2 响应格式（严格 JSON）

要求 LLM **仅**返回一个 JSON 对象，且不要用 markdown 代码块包裹。示例：

```json
{
  "done": false,
  "reason": "关闭弹窗后需再取 snapshot 找评论框",
  "steps": [
    { "op": "click", "uid": "wce-abc123" }
  ]
}
```

或任务完成时：

```json
{
  "done": true,
  "reason": "已点击提交按钮",
  "steps": []
}
```

- **done**：是否结束任务；为 true 时不再进行下一轮。  
- **reason**：简短说明，便于日志与排查。  
- **steps**：本轮要执行的操作列表；顺序执行，任一失败可配置为整轮失败或继续执行其余步骤（MVP 建议整轮失败即终止本任务）。

### 7.3 解析与校验

- Background 从 LLM 返回文本中抽取 JSON（兼容前后有 markdown 或说明文字）。  
- 校验：`steps` 中每项必须为 `{ op: 'click'|'fill', uid: string }` 或 `{ op: 'fill', uid: string, value: string }`；非法项丢弃或整条解析失败并终止任务。  
- 不执行 op 以外的任何指令，避免注入风险。

## 八、与现有批量流程的对接（MVP 边界）

- **入口**：在 Side Panel 或 Background 的「批量提交」逻辑中，为每条 URL 增加一个开关或策略：「使用完全 AI 识别」时，不调用 content 的 `blogCommentGenerateAndFill`，改为调用本方案的单任务执行器。  
- **输入**：`tabId`、`siteUrl`、`generatedComment`（评论正文可由现有 `generateBlogComment` 或一发接口预先生成）。  
- **输出**：统一为 `{ success: boolean, needManualVerify?: boolean, error?: string }`；后续「验证本次提交」与飞书回写仍沿用现有逻辑，仅数据来源从 formHandler 改为本方案。  
- **MVP 不实现**：批量列表 UI、飞书凭证、回写接口的改动；仅实现「单 Tab 单任务」的完整闭环，并在单页或批量中可开关使用。

## 九、MVP 验收标准

1. **Snapshot**：在任意可访问的 Blog 页面上，Content 能返回包含可交互节点（至少包含若干 button/link/textbox）的 snapshotText，且每个可操作节点带唯一 uid（data-wce-nodeid）。  
2. **执行**：给定合法 uid，Content 能正确执行 click 或 fill，且页面有可见反应（如弹窗关闭、输入框出现文字）。  
3. **单轮 E2E**：Background 取 Snapshot → 调用 LLM（可 mock 或真实）→ 解析 steps → 下发执行，整条链路无报错且执行结果与预期一致（可用固定 mock 响应验证）。  
4. **多轮与终止**：在「关弹窗 → 填评论 → 点提交」的 2～3 轮场景下，能按 done 或 MAX_TURNS/超时正确终止，且不依赖任何 MCP。  
5. **超时**：单轮超时与总任务超时能触发，并返回明确超时结果，不卡死。

## 十二、总结

- **方案 B** 在扩展内自建「整页 Snapshot + UID 操作 + 多轮 LLM」的轻量 Agent，**不依赖 AIPex 运行时与任何 MCP**。  
- **Snapshot**：Content 内 DOM 遍历、`data-wce-nodeid` 赋值、树结构 + 文本格式化，发给 LLM。  
- **UID 解析与执行**：Content 内通过 `data-wce-nodeid` 查元素并执行 click/fill，消息协议明确。  
- **多轮与超时**：最大轮数、单轮超时、总任务超时、LLM done 及错误终止，均在 Background 内实现。
