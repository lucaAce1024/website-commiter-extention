# 完全 AI 识别提交方案 — 基于 AIPex 的终极方案评估与设计

## 一、当前批量提交遇到的问题归纳

在测试「可提交 comment 的网站列表」时，现有**规则 + AI 表单识别**方案无法完全匹配定位检测规则，出现以下典型问题：


| 问题类型                       | 表现                                        | 根因简述                                                                          |
| -------------------------- | ----------------------------------------- | ----------------------------------------------------------------------------- |
| **隐私/ Cookie 弹窗**          | 页面打开后先出现「同意 Cookie」「隐私政策」等弹窗，遮挡或覆盖评论区域    | 当前流程没有「先关闭弹窗」的步骤，直接基于 DOM 找 form/input，弹窗存在时可能误识别或找不到目标                       |
| **Use cookies 弹窗**         | 与上类似，需先点击「Accept」/「同意」才能操作主内容             | 同上，规则驱动流程假定「页面已干净」                                                            |
| **找不到提交按钮**                | 页面上只有评论输入框，没有明显的 Submit/Post 按钮，或按钮在非标准位置 | 现有逻辑依赖「form 内 input[type=submit]/button」或兄弟节点补全，部分站点用 div+click 或自定义控件，规则覆盖不到 |
| **仅 comment 框 + 必须带 link** | 站点只留一个评论输入框，且业务上要求评论内容中必须包含链接才算提交成功       | 当前流程没有「按站点/页面类型」让 AI 决定「在评论中插入 link」并判断提交是否完成，更多是固定字段映射                       |


**共性根因**：当前实现是 **规则驱动 + 单次 AI 识别**——先假设页面结构（有 form、有 submit 按钮、无弹窗），再用 AI 做「字段映射 + 评论生成」。一旦页面不符合假设（弹窗、非常规布局、仅 comment+link），就无法可靠完成。

## 二、AIPex 项目能力概览

AIPex 位于 `git_repo_autopilot/AIPex`，是一个**开源浏览器自动化 Agent**，在现有 Chrome 中以扩展形式运行，用自然语言驱动多轮操作。与当前需求相关的能力如下。

### 2.1 页面理解：Snapshot（可访问性树 / DOM 树）

- **take_snapshot**：对当前 Tab 生成页面的**可访问性快照**（CDP 模式用 Accessibility API，非 CDP 模式用 `@aipexstudio/dom-snapshot` 的 DOM 遍历）。
- 返回的是**带 UID 的交互元素树**（按钮、链接、输入框、复选框等），以**文本形式**提供给 LLM，便于模型理解「整页结构」而不是我们写死的选择器。
- **search_elements**：在快照文本上做 grep/glob 搜索，便于快速定位「Accept」「Submit」「Comment」等关键词对应元素。

因此，**弹窗上的「Accept」、非常规的「提交」控件、仅有的评论输入框**，只要在可访问性树/ DOM 中有对应节点，都能被看到并带上 UID，不依赖我们预先定义的 form/button 规则。

### 2.2 操作方式：基于 UID 的点击与填写

- **click**：通过 `tabId + uid` 点击任意元素（来自 snapshot）。
- **fill_element_by_uid**：对指定 uid 的输入框填入文本。
- **fill_form**：批量对多组 `{ uid, value }` 填写，并支持滚动、模拟鼠标等。
- **hover_element_by_uid**：悬停。

所有操作都基于「当前 snapshot 中的 uid」，不依赖 name/id/selector 规则，因此**任何可见可交互元素**（包括弹窗按钮、自定义提交控件）都可被操作。

### 2.3 Agent 执行模式：多轮决策

- 用户输入自然语言任务（如 "Close cookie banner and submit a comment with this link"）。
- Agent 可**多轮**：`take_snapshot` → LLM 根据 snapshot 决定下一步（如先 click 某 uid 关弹窗）→ 执行 → 再 `take_snapshot` → 再决定（如 fill comment、再 click submit）→ … 直到任务完成或达到上限。

因此，**先关弹窗、再找评论框、再填评论（含 link）、再找并点提交**，可以在一段任务描述下由 Agent 自主多步完成，而不是我们写死「第一步关弹窗、第二步填 form」。

### 2.4 与现有 website-commiter 的对比（简要）


| 维度               | 当前 website-commiter（规则 + 单次 AI） | AIPex（整页 snapshot + 多轮 Agent） |
| ---------------- | ------------------------------- | ----------------------------- |
| 页面假设             | 有 form、有 submit、无弹窗             | 无强假设，整页可见即可操作                 |
| 弹窗               | 不处理                             | 可由 AI 识别并先 click 关闭           |
| 提交按钮             | 依赖 form 内/兄弟节点 button           | 任意可点击元素，只要 snapshot 中有        |
| 仅 comment + link | 未专门建模                           | 任务描述中可明确「评论中带 link 并提交」       |
| 扩展形态             | 自研扩展                            | Chrome 扩展，可被引用或借鉴             |

## 三、AIPex 能否解决上述问题（逐条）


| 问题                    | 能否解决 | 说明                                                                                          |
| --------------------- | ---- | ------------------------------------------------------------------------------------------- |
| 隐私确认弹窗                | ✅ 能  | 先 take_snapshot，AI 识别「同意/Accept」类按钮的 uid，click 关闭后再继续                                       |
| Use cookies 弹窗        | ✅ 能  | 同上，视为一种 consent 弹窗，由 Agent 在首轮或前几轮处理                                                        |
| 找不到提交按钮               | ✅ 能  | Snapshot 包含所有可交互元素（含 div+role、自定义按钮），AI 可选「最像提交」的 uid 点击；若只有 comment 框，可配合「评论中带 link」的策略    |
| 只留 comment 框且必须带 link | ✅ 能  | 任务描述中明确「在评论内容中包含 [siteUrl]」，由 Agent fill 评论框；提交方式可由 AI 根据 snapshot 决定（如无按钮则尝试回车或找「Post」链接等） |


**结论**：AIPex 的「整页 snapshot + uid 操作 + 多轮 Agent」架构，能够从原理上覆盖当前遇到的四类问题，可作为**完全 AI 识别提交**的终极方案基础。

## 四、方案设计：如何用 AIPex 解决

### 4.1 思路概述

- **批量提交的每一站**：不再仅调用现有 `formHandler` 的「识别评论表单 → 填充 → 点击提交」。
- 改为在**当前 Tab** 上运行一段「AI 驱动」的流程，任务目标为：  
**关闭任何 cookie/隐私弹窗 → 找到评论输入区域并填入给定评论（评论中必须包含站点链接）→ 找到并点击提交/发布控件 → 完成**。
- 执行层可以：**直接复用 AIPex 的 Agent + tools**，或**借鉴其 snapshot/uid 机制在 website-commiter 内自建一套**。

### 4.2 方案 A：直接集成 AIPex Agent（推荐用于验证与快速落地）

- **做法**：将 AIPex 作为**依赖或子模块**引入 website-commiter-extention；或通过 **Chrome 扩展消息/ Native Messaging** 与已安装的 AIPex 扩展通信。
- **批量提交单条流程**：  
  1. Background 打开目标 URL 的 Tab，等待加载完成。
  2. 调用 AIPex 的 Agent，传入任务描述，例如：
    `Close any cookie or privacy consent dialog if present. Then find the comment input, fill it with the following text (the text must include the link: ${siteUrl}): "${generatedComment}". Then find and click the submit/post button to publish the comment.`
  3. AIPex 内部多轮 take_snapshot / click / fill_element_by_uid，直到完成或超时。
  4. 本扩展再执行「验证本次提交」（在当前页查找站点链接）、飞书回写等后续逻辑。
- **优点**：直接复用成熟实现，快速验证「完全 AI 识别」是否解决弹窗/无按钮/仅 comment+link 等问题。  
- **缺点**：依赖 AIPex 的安装与版本、API 稳定性；需设计清晰的「任务描述 + 返回结果」协议。

### 4.3 方案 B：借鉴 AIPex 架构，在 website-commiter 内自建「轻量 Agent」

- **做法**：不依赖 AIPex 代码库，但在本扩展内实现：  
  1. **整页 Snapshot**：用 CDP Accessibility API 或 AIPex 的 `@aipexstudio/dom-snapshot`（可仅引用该包）生成带 uid 的可访问性/ DOM 树文本。
  2. **单轮/多轮 LLM 调用**：将 snapshot + 任务描述发给 LLM，要求返回「操作序列」，例如：
    `[{ "action": "click", "uid": "xxx" }, { "action": "fill", "uid": "yyy", "value": "..." }, ...]`
  3. **Content Script 或 Background 执行**：根据 snapshot 中的 uid 解析回 DOM 节点并执行 click/fill（可参考 AIPex 的 `DomElementHandle` / `SmartElementHandle`）。
  4. 若未检测到「提交成功」或页面变化，可**再取一次 snapshot** 再问 LLM，实现简单多轮。
- **优点**：无 AIPex 运行时依赖，逻辑完全在本项目内，可深度定制（如只做「关弹窗 + 评论提交」）。  
- **缺点**：需自实现 snapshot 格式化、uid 解析与执行、多轮终止条件与超时，开发量大于方案 A。

### 4.4 方案 C：混合模式（渐进式）

- **默认**：仍用现有「规则 + AI 表单识别」流程；若某条 URL 在批量中**识别失败或验证失败**，可对该 Tab **自动 fallback 到「完全 AI 识别」**（方案 A 或 B）。  
- 这样在「正常站点」上保持现有逻辑与性能，在「问题站点」上用 AI 多轮操作兜底，平衡体验与实现成本。

### 4.5 任务描述与参数约定（适用于方案 A / B）

建议在任务描述中显式传入以下变量，便于 Agent 或 LLM 输出正确行为：

- **siteUrl**：当前站点档案的网站 URL，评论中必须包含此链接。  
- **generatedComment**：已生成的评论正文（可先由现有 `generateBlogComment` 或一发接口得到），Agent 负责填入并确保与 siteUrl 组合（如文末附 link）。  
- **optional: 关弹窗关键词**：如 "Accept", "同意", "Allow all", "I agree"，便于 prompt 中提示模型优先识别这类按钮。

提交成功的判定可与现有逻辑一致：提交后等待页面刷新/变化，再在当前页查找指向 siteUrl 的链接，存在即「检测成功」。

## 五、实施步骤建议（以方案 A 为例）

1. **PoC（概念验证）**
  - 在本地让 AIPex 扩展与 website-commiter 能通信（或把 AIPex 的 snapshot + element tools 抽成可在本扩展调用的模块）。  
  - 对 1～2 个「有 cookie 弹窗」或「仅 comment 框」的站点，用固定任务描述跑通：关弹窗 → 填评论（含 link）→ 点提交。
2. **协议与接口设计**
  - 定义「批量提交单条」的输入：`url, siteUrl, generatedComment, options`。  
  - 定义输出：`success, needManualVerify, errorMessage`，以及可选的「最后 snapshot 摘要」便于排查。
3. **与现有批量流程对接**
  - Background 在「打开 Tab → 加载完成」后，不再调 content 的 `blogCommentGenerateAndFill`，改为调 AIPex 驱动流程（或自建轻量 Agent）。  
  - 保留「验证本次提交」与飞书回写逻辑不变。
4. **配置与降级**
  - 在 Side Panel/options 中增加「使用完全 AI 识别（AIPex/轻量 Agent）」开关；若未开启或调用失败，则回退到现有规则+AI 表单识别流程。
5. **测试与回归**
  - 用当前问题列表（隐私弹窗、cookies 弹窗、无提交按钮、仅 comment+link）逐站回归；  
  - 同时抽若干「原本就正常」的站点，确保混合/降级模式下行为不变。

## 六、风险与注意事项

- **依赖与兼容**：若采用方案 A，需考虑 AIPex 的 Chrome 版本要求、Manifest 权限（如 debugger 用于 CDP snapshot），以及与本扩展的权限与生命周期兼容。  
- **成本与延迟**：多轮 snapshot + LLM 会带来更多 token 与延迟，建议对「完全 AI 识别」做单条超时与整批并发控制。  
- **稳定性**：不同站点 DOM/ a11y 树差异大，Agent 可能偶尔选错 uid（如点到「拒绝」而非「接受」），可在任务描述中强调「只点击同意/接受类按钮」，并记录失败案例用于 prompt 或规则微调。  
- **合规与伦理**：自动关 cookie 弹窗、自动填评论属于自动化行为，需确保符合目标站点 ToS 与隐私政策，必要时仅对「用户已授权」的站点列表启用。

## 八、总结

- **当前问题**：规则驱动的评论识别与提交无法应对隐私/cookie 弹窗、无常规提交按钮、仅 comment 框且须带 link 等多样站点。  
- **AIPex 能力**：整页 snapshot（可访问性/DOM）+ 基于 uid 的 click/fill + 多轮 Agent，可从原理上覆盖上述场景。  
- **推荐路线**：先用**方案 A** 做 PoC，验证「完全 AI 识别」在问题站点上的效果；再视情况保留为可选能力或落地**方案 B** 自建轻量 Agent；批量流程中可通过**方案 C** 做混合与降级，兼顾稳定性与覆盖率。  
- 最终将「完全 AI 识别提交」作为批量提交的**增强模式**，与现有规则+AI 表单识别并存，由用户或策略选择使用。
