# 扩展内自建：实现路径、复杂度与开源方案

本文回答三件事：**扩展里如何自建**四层能力、**复杂度有多高**、**有没有成熟开源方案**可参考或复用。

---

## 一、扩展中如何自建（按层拆解）

### 1. 感知层（Snapshot）

**做什么**：在 Content Script 里遍历当前页 DOM，给可交互节点打 UID，生成树形文本供 LLM 使用。

**实现路径**：


| 步骤       | 做法                                                                                                     | 代码量级       |
| -------- | ------------------------------------------------------------------------------------------------------ | ---------- |
| 遍历 DOM   | 从 `document.body` 递归，按 tag/role/可见性过滤（保留 button/input/textarea/select/a、带 role 或 cursor:pointer 的 div） | ~150～250 行 |
| 分配 UID   | 对每个保留节点：无 `data-wce-nodeid` 则生成 `wce-${Date.now().toString(36)}-${cnt}` 并 `setAttribute`               | ~30 行      |
| 建树 + 序列化 | 构造 `SnapshotNode { id, role, name, value, children }`，再递归格式化成「缩进 + uid + role + name」文本                | ~80～120 行  |
| 消息接口     | 监听 `fullAiTakeSnapshot`，返回 `{ snapshotText, snapshotResult }`                                          | ~20 行      |


**合计**：约 **300～450 行** 的独立 JS 模块（如 `content/fullAiSnapshot.js`）。难点在「哪些算可交互、如何稳定取 name/label」，可先做宽松规则再迭代收紧。

---

### 2. 行动层（按 UID 执行）

**做什么**：在目标 Tab 内根据 uid 找到元素并执行 click / fill。

**实现路径**：


| 步骤    | 做法                                                                                     | 代码量级  |
| ----- | -------------------------------------------------------------------------------------- | ----- |
| 查元素   | `document.querySelector('[data-wce-nodeid="' + cssEscape(uid) + '"]')`，可选同源 iframe 内查找 | ~40 行 |
| click | `el.scrollIntoView()` 后 `el.click()` 或 `dispatchEvent(new MouseEvent(...))`            | ~25 行 |
| fill  | `el.value = value`，再 `dispatchEvent` input/change；兼容 contenteditable 可后补               | ~35 行 |
| 消息接口  | 监听 `fullAiExecute`，解析 `steps[]`，逐条执行并汇总结果返回                                            | ~50 行 |


**合计**：约 **150～200 行**。可与 Snapshot 放在同一 content 文件或单独 `fullAiExecute.js`，由 manifest 注入同一 script。

---

### 3. 控制层（多轮循环 + 终止 + 超时）

**做什么**：在 Background 里跑「取 Snapshot → 调 LLM → 下发执行 → 判断是否继续」。

**实现路径**：


| 步骤   | 做法                                                                                                                        | 代码量级  |
| ---- | ------------------------------------------------------------------------------------------------------------------------- | ----- |
| 单轮逻辑 | `async function runOneRound(tabId, taskDesc, round)`：sendMessage 取 Snapshot → 拼 prompt 调现有 LLM → 解析 JSON → sendMessage 执行 | ~80 行 |
| 循环   | `while (!done && round < MAX_TURNS && !totalTimeout)` 调用 `runOneRound`，轮间 delay                                           | ~30 行 |
| 超时   | `Promise.race([ runOneRound(), timeout(ROUND_TIMEOUT_MS) ])`；每轮前检查 `Date.now() - startTime > TASK_TIMEOUT_MS`             | ~25 行 |


**合计**：约 **130～150 行**，可放在 `background.js` 新分支或 `lib/fullAiAgent.js`。难点是错误与超时时的状态清理和返回格式统一。

---

### 4. 协议层（LLM 输入输出）

**做什么**：固定 prompt 模板和返回 JSON 的解析与校验。

**实现路径**：


| 步骤        | 做法                                                                                         | 代码量级  |
| --------- | ------------------------------------------------------------------------------------------ | ----- |
| Prompt 模板 | 字符串模板：任务描述 + `siteUrl`/`generatedComment` + 当前轮次 + Snapshot 文本；要求「只输出 JSON，不要 markdown」    | ~40 行 |
| 解析        | 从 LLM 返回文本中抽 JSON（可兼容前后有 markdown 或说明），`JSON.parse` + 校验 `steps` 每项为 `{ op, uid, value? }` | ~50 行 |


**合计**：约 **90 行**，通常和控制层一起放在 Background 侧。

---

### 自建总览


| 层      | 位置         | 约行数             | 依赖                         |
| ------ | ---------- | --------------- | -------------------------- |
| 感知层    | Content    | 300～450         | 无，仅 DOM API                |
| 行动层    | Content    | 150～200         | 无                          |
| 控制层    | Background | 130～150         | 现有 LLM 调用、tabs.sendMessage |
| 协议层    | Background | ~90             | 无                          |
| **合计** | —          | **约 670～890 行** | 无新增 npm 包                  |


---

## 二、复杂度有多高？

**总体：中等偏下。**

- **技术风险**：低。全是 DOM 遍历、消息通信、Promise 与超时，无复杂算法或新运行时。
- **主要工作量**：
  - **感知层**：把「可交互」定义清楚并兼容各种站点（表单在 iframe、动态插入的按钮等），需要多站试跑和迭代；首版可先只做「主文档 + 常见 tag/role」。
  - **协议层**：LLM 有时会多输出几句话或 markdown 包裹，解析要鲁棒（正则/截取首尾 `{}` 等）。
- **与现有代码的关系**：不替换现有 formHandler，只是新增 content 脚本和 background 的一条分支；批量流程里「用完全 AI 识别」时调新入口即可。

**粗略工期**：1 人 3～5 个工作日可完成 MVP 闭环（单页多轮能跑通）；再 1～2 天做 2～3 个站点的适配与边界处理。

## 三、成熟的开源方案

### 3.1 可直接复用或拷贝的


| 方案                                                                                     | 用途  | 说明                                                                                                                                                                                    |
| -------------------------------------------------------------------------------------- | --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **AIPex 的 dom-snapshot**（`AIPex/packages/dom-snapshot`）                                | 感知层 | MIT。DOM 遍历、可交互节点识别、`data-aipex-nodeid` 赋值、树结构与格式化一应俱全。**不 npm 依赖**的前提下，可**拷贝或移植**其 `collector.ts` / `snapshot-formatter.ts` 到本项目中（改为 `data-wce-nodeid`），能省掉大部分自写 Snapshot 逻辑，复杂度显著下降。 |
| **AIPex 的 DomLocator / runDomAction**（`browser-runtime/src/automation/dom-locator.ts`） | 行动层 | 按 UID 在页面内 click/fill 的注入函数与消息协议，可直接参考或拷贝到 content 中，把 `data-aipex-nodeid` 换成 `data-wce-nodeid` 即可。                                                                                   |


以上两处是**最值得借鉴的开源实现**，同方案 B、同技术栈，且已在真实扩展中验证。

---

### 3.2 可参考但需适配的


| 方案                                                                                        | 用途    | 说明                                                                                      |
| ----------------------------------------------------------------------------------------- | ----- | --------------------------------------------------------------------------------------- |
| **acc-snapshot**（[jurokapsiar/acc-snapshot](https://github.com/jurokapsiar/acc-snapshot)） | 感知层   | 从 DOM/AOM 生成可访问性快照，MIT。体量小、星少，若要在扩展里用需自己加「可交互过滤 + UID 写入」和文本格式化，适合作为 a11y 结构的参考，而非开箱即用。 |
| **Puppeteer / Playwright 的 Accessibility.snapshot()**                                     | 感知层思路 | 思路与我们需要的一致，但运行在 **Node 环境**，依赖 CDP。扩展里无法直接调用；可借鉴其「interesting 节点」过滤和树形结构，用 DOM 自建一版。    |


---

### 3.3 没有现成替代的


| 需求                                             | 现状                                                                                      |
| ---------------------------------------------- | --------------------------------------------------------------------------------------- |
| **扩展内「完整 Agent」**（感知 + 行动 + 多轮控制 + 协议，不依赖 MCP） | **没有**其他成熟开源扩展做到与 AIPex 同形态。AIPex 是「扩展 + Agent + 可选 MCP」；纯扩展内、无 MCP 的轻量 Agent 多为项目自建。   |
| **Chrome 扩展 + LLM 多轮 + 页面操作**                  | 开源里几乎只有 AIPex 及其依赖的 `@openai/agents`；我们方案 B 不用其运行时，只借鉴 dom-snapshot / DomLocator 的实现细节。 |


结论：**感知层和行动层**有 AIPex 的成熟实现可拷贝/移植；**控制层与协议层**没有现成的「扩展内、无 MCP」的库，需要自己写，但逻辑简单、代码量不大。

---

## 四、推荐实施策略

1. **感知层**：优先从 AIPex 的 `dom-snapshot` **拷贝或移植** collector + formatter 到本项目（改为 `data-wce-nodeid`、单文件或少量 JS），把自写 Snapshot 工作量压到最低。
2. **行动层**：参考 AIPex 的 `dom-locator.ts` 中 `runDomAction` 的查询与 click/fill 实现，在 content 里实现等价的 `fullAiExecute` 逻辑。
3. **控制层 + 协议层**：按设计书自写，约 200 行量级，无现成库可替代，但结构清晰、易测。
4. **整体**：在「不引入 AIPex 包、不依赖 MCP」的前提下，通过**借鉴/拷贝 AIPex 的 dom-snapshot 与 DomLocator**，把自建复杂度从「中高」降到「中等偏下」，MVP 约 3～5 天可完成。

---

## 五、小结


| 问题             | 简要回答                                                                                                                     |
| -------------- | ------------------------------------------------------------------------------------------------------------------------ |
| **扩展中如何自建？**   | 分四层：Content 内实现 Snapshot（遍历+UID+格式化）与 Execute（按 uid click/fill）；Background 内实现多轮调度、超时与 LLM 请求/解析；协议用固定 prompt + JSON 校验。 |
| **复杂度有多高？**    | 中等偏下；合计约 670～890 行，无新运行时；主要时间花在「可交互」规则与多站适配、LLM 输出解析的鲁棒性。                                                                |
| **有没有成熟开源方案？** | **有可复用/可抄的**：AIPex 的 dom-snapshot 与 DomLocator，拷贝或移植可大幅降低感知层和行动层工作量。**没有**现成的「扩展内、无 MCP、完整 Agent」替代品，控制层与协议层需自建。         |
