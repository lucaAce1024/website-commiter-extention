# 轻量 Agent 构建原理说明

本文解释「轻量 Agent」是什么、如何运转，以及**除了 AI API 之外**还需要哪些必要条件，才能把「AI 决策」变成真实可用的页面自动化。

---

## 一、Agent 在这里指什么？

在我们这个场景里，**Agent** 不是指一个常驻的「智能体进程」，而是指一套**闭环流程**：

- **目标**：在任意网页上完成「关弹窗 → 填评论（含链接）→ 点提交」。
- **难点**：每个站点结构不同（弹窗样式、按钮位置、是否只有评论框），无法用固定规则穷举。
- **思路**：让 AI **根据当前页面长什么样**，**自己决定下一步做什么**，然后我们**把它的决定变成真实操作**；做完一步后**再看一眼页面**，再决定下一步……直到任务完成或超时。

所以「轻量 Agent」= **「感知 → 思考 → 行动」的循环**，其中「思考」交给 AI API，其余全部由我们自己的代码完成。

---

## 二、核心循环：感知 → 思考 → 行动

可以抽象成下面这三步，不断重复：

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│  感 知      │ ──▶ │  思 考      │ ──▶ │  行 动      │
│ (看页面)    │     │ (AI 决策)   │     │ (执行操作)  │
└─────────────┘     └─────────────┘     └─────────────┘
       ▲                                         │
       └─────────────────────────────────────────┘
                     (下一轮：再感知)
```

- **感知**：拿到「当前页面长什么样」的一份描述，并且这份描述要**既能给人/模型理解**，又能**和页面上的真实元素一一对应**（否则无法执行）。
- **思考**：把「任务说明 + 当前页面描述」发给 AI，让它输出「下一步做什么」——例如：点哪个按钮、在哪个框里填什么。
- **行动**：根据 AI 的输出去**真实地**点击、填写，并保证操作的是「AI 指的那个元素」。

**仅靠 AI API 做不到自动化**：API 只会「输入文本 → 输出文本」。它既看不到浏览器里的 DOM，也点不了按钮。所以我们必须自己实现「感知」和「行动」，并用固定格式把二者与「思考」衔接起来。

---

## 三、除 AI API 之外的四个必要条件

下面四项都是**必须**的；少掉任何一块，循环都转不起来。

### 1. 感知层：把「页面」变成「AI 能读的文本 + 可回溯的标识」

**要解决的问题**：AI 只能处理文本，而页面是 DOM 树。如何既让 AI 理解页面结构，又能在执行时精确找到「AI 说的那个按钮」？

**做法**：

- 在页面里做一次**有选择的遍历**（只保留可点击、可填写的元素和少量关键文本），为每个需要操作的节点生成一个**唯一 ID（UID）**，并写入 DOM（例如 `data-wce-nodeid="wce-xxx"`）。
- 再把这些节点整理成**树形文本**（每行一个节点，带缩进、角色、文案、UID），发给 LLM。

这样：

- **AI 看到的是**：一行行带 `uid=wce-abc`、`button "Accept"` 之类的描述，能理解「有个 Accept 按钮」。
- **执行时**：我们拿着 AI 返回的 `uid=wce-abc`，在页面里用 `querySelector('[data-wce-nodeid="wce-abc"]')` 找到唯一元素并点击。

**因此，感知层的必要产出是**：

- 一份**发给 LLM 的 Snapshot 文本**（格式固定、长度可控）；
- 一套**UID 与 DOM 元素的对应关系**（通过属性挂在 DOM 上，执行时按 UID 查找）。

没有这一层，AI 就相当于「盲人」，无法根据页面做决策；没有 UID，AI 说「点 Accept」我们也无法稳定地映射到具体元素。

---

### 2. 行动层：把「AI 的输出」变成「浏览器里的真实操作」

**要解决的问题**：AI 返回的是 JSON，例如 `{ "op": "click", "uid": "wce-abc" }`。谁去点？在哪页点？

**做法**：

- 在**目标 Tab 的页面上下文**里（Content Script 或注入脚本），根据 `uid` 用 `querySelector` 找到元素，然后：
  - `op === "click"` → 调用 `element.click()` 或派发点击事件；
  - `op === "fill"` → 设置 `element.value` 并触发 `input`/`change` 等事件。

**因此，行动层的必要条件是**：

- 能在**目标页面**里执行脚本（扩展的 Content Script 或 `scripting.executeScript`）；
- 有**统一的执行协议**：例如只接受 `click(uid)` 和 `fill(uid, value)`，拒绝任意代码执行，保证安全且可重复。

没有这一层，AI 的决策就只是「纸上谈兵」，页面不会有任何变化。

---

### 3. 控制层：多轮循环与终止、超时

**要解决的问题**：一页操作往往需要多步（先关弹窗，再填框，再点提交）。何时继续下一轮？何时停止？如何避免死循环或长时间卡住？

**做法**：

- **循环**：每轮 = 一次「感知 → 思考 → 行动」；本轮执行完后等待短暂时间（如 1 秒），再取一次 Snapshot，进入下一轮。
- **终止条件**（满足其一即停）：
  - AI 明确返回「任务完成」（如 `done: true`）；
  - 已达到最大轮数（如 10 轮）；
  - 单轮耗时超时（如 25 秒）；
  - 总任务耗时超时（如 90 秒）；
  - 执行报错且不可恢复（如元素找不到）。

**因此，控制层的必要条件是**：

- 在 **Background** 里实现「取 Snapshot → 调 LLM → 下发执行 → 判断是否继续」的**显式状态机**；
- 用 **Promise.race + 计时** 实现单轮与总任务超时，避免无限等待。

没有这一层，要么只做一步就停，要么可能无限循环或长时间挂起。

---

### 4. 协议层：输入输出格式的严格约定

**要解决的问题**：AI 的输出是自然语言或松散 JSON，我们需要的却是「可解析、可执行」的指令。若格式不统一，解析会失败或执行错对象。

**做法**：

- **给 AI 的输入**：固定模板（任务说明 + 当前轮次 + Snapshot 文本），并明确要求「只输出指定 JSON，不要 markdown 包裹、不要多余解释」。
- **要求 AI 的输出**：例如只接受 `{ done?: boolean, steps: [ { op: "click"|"fill", uid: string, value?: string } ] }`；解析时校验类型与必填字段，非法则丢弃或终止本轮。

**因此，协议层的必要条件是**：

- **请求格式**：任务描述 + Snapshot 文本的结构固定，便于 prompt 稳定；
- **响应格式**：严格 JSON schema，并在代码里做解析与校验，不执行约定外的操作。

没有这一层，多轮之间无法稳定衔接，也容易产生安全或行为不确定问题。

---

## 四、小结：轻量 Agent = 四块拼图 + AI API

| 条件 | 作用 | 没有会怎样 |
|------|------|------------|
| **AI API** | 根据「任务 + 当前页面描述」输出下一步操作 | 没有「思考」，无法决策 |
| **感知层** | 把页面变成「Snapshot 文本 + UID 与 DOM 的对应」 | AI 看不到页面，无法做针对性决策；执行时也找不到元素 |
| **行动层** | 按 UID 在目标页执行 click/fill | AI 的决策无法变成真实操作 |
| **控制层** | 多轮循环、终止条件、超时 | 只能做一步，或死循环/长时间卡住 |
| **协议层** | 固定的请求/响应格式与解析 | 无法稳定解析与执行，行为不可控 |

所以：**除了 AI API 之外，轻量 Agent 还需要「感知层、行动层、控制层、协议层」这四类必要条件**。在设计书里，它们分别对应：

- 感知层 → Snapshot 采集、UID 分配、文本格式化；
- 行动层 → UID 解析、click/fill 执行、消息协议；
- 控制层 → 多轮调度、终止条件、单轮/总超时；
- 协议层 → LLM 的 prompt 模板与返回 JSON 的约定与解析。

把这四块和现有 AI 接口接好，就构成了可运转的「轻量 Agent」闭环。

---

## 五、AIPex 能否弥补这块缺失？

**能。** AIPex 已经实现了上述四层能力，若采用**方案 A（集成 AIPex）**，就不必在项目内从零自建这四块；AIPex 可以直接「弥补除 AI API 之外的缺失」。

对应关系如下。

| 必要条件 | AIPex 中的对应能力 | 说明 |
|----------|--------------------|------|
| **感知层** | `take_snapshot`、DOM/CDP 双模式、`formatSnapshot`、`data-aipex-nodeid` | 在目标页采集可交互节点并打 UID，输出树形文本给模型；支持 DOM 模式（无需 debugger）。 |
| **行动层** | `click`、`fill_element_by_uid`、`fill_form`、`DomLocator` / `SmartElementHandle` | 按 UID 在目标 Tab 内执行点击、填写；通过消息或注入脚本在页面上下文执行。 |
| **控制层** | Agent 的 `runExecution`、`maxTurns`、Session | 多轮「取 snapshot → 调模型 → 执行 tool_calls → 再取 snapshot」的循环由 AIPex 内部完成。 |
| **协议层** | 基于 OpenAI Agents SDK 的 **Tool Calling** | 模型通过 `tool_calls` 返回要调用的工具名与参数（如 `click(tabId, uid)`），Runner 执行工具并把结果塞回对话，无需我们自定「done + steps」的 JSON 协议。 |

因此：**用 AIPex = 感知、行动、控制、协议四层都由 AIPex 提供**，我们主要做三件事：

1. **提供 AI API**（或接入 AIPex 支持的 API）。
2. **写清任务描述**：用自然语言告诉 AIPex「关 cookie 弹窗、填评论（含某链接）、点提交」。
3. **与现有流程对接**：在批量提交里调用 AIPex 跑完单条任务，再走验证、飞书回写。

**代价**：AIPex 部分能力（如技能、干预等）依赖**本地 MCP Server**；若不想依赖 MCP 或希望扩展「装好即用、无本地服务」，就选**方案 B（自建）**，在扩展内实现这四层——设计书里写的 Snapshot、UID 执行、多轮与超时、协议约定，就是在补「不接入 AIPex 时的缺失」。

**结论**：  
- **方案 A**：AIPex **能**弥补四层缺失，省掉自建，需接受其运行形态（含可选 MCP）。  
- **方案 B**：不依赖 AIPex，由我们在扩展内自建四层，无 MCP、无额外进程，但实现与维护成本在己方。
