# 评论识别流程说明与「一发请求」实现方案

## 一、当前识别流程与局限性

### 1.1 当前数据流（两路独立）

| 步骤 | 评论表单字段识别 | 评论内容生成 |
|------|------------------|--------------|
| 触发 | Popup 点「生成评论并填充」→ Content 先 `recognizeCommentForm(useLlm: true)` | 同上流程中再发 `generateBlogComment(title, description)` |
| 数据来源 | Content：`getCommentFormMetadata()` → 得到 `formMetadata`（含 fields + formHtml） | Content：`document.title` + `meta[name="description"]` |
| 发送 | `chrome.runtime.sendMessage({ action: 'aiRecognizeCommentForm', formMetadata })` | `chrome.runtime.sendMessage({ action: 'generateBlogComment', title, description })` |
| 处理 | Background：`handleAIRecognizeCommentForm(formMetadata)`，用 formDescription 或 formHtml 拼 prompt，一次 LLM 调用 | Background：`handleGenerateBlogComment(title, description)`，一次 LLM 调用 |
| 返回 | `{ mappings, submitButton }`，mappings 中每项带 `locator`（来自 formMetadata.fields[fieldIndex]） | `{ comment }` 评论文本 |
| 使用 | Content 用 mappings + submitButton 做填充、点提交 | Content 把 comment 填入 comment 字段 |

即：**两次独立 API 请求**（先识别表单，再生成评论），且识别依赖 Content 提供的 `formMetadata`。

### 1.2 formMetadata 的构建方式（Content 侧）

- **getFormMetadata()**（formHandler.js）：
  - 遍历 **所有** `document.querySelectorAll('form')`，把每个 form 内的 `input/textarea/select`（排除 hidden/submit/button/reset）按顺序推进一个 **扁平数组** `fields`。
  - 同时收集自定义控件（contenteditable、Categories/Tags 等）。
  - **formHtml** 取的是 **第一个 form**：`const firstForm = document.querySelector('form'); formHtml = firstForm?.outerHTML.slice(0, 12000)`。
- **getCommentFormMetadata()**：
  - 直接复用上述 `getFormMetadata()` 的返回值，再往 `fields` 里 **追加** 所有 form 的 submit/button。
  - 因此 **formHtml 只对应“第一个 form”**，而 **fields 是“所有 form”的字段按顺序拼接**。

带来的问题：

1. **多 form 时 HTML 与 fields 不对齐**  
   若页面先有搜索/订阅 form，后有评论 form，则：
   - 发给 AI 的 HTML 是「搜索 form」；
   - AI 返回的 fieldIndex 是按这段 HTML 里 input/textarea 顺序编号的；
   - 但解析时用 `formMetadata.fields[fieldIndex]` 取 locator，而 `fields` 里前几项是第一个 form 的，后面才是评论 form 的。  
   → **fieldIndex 与真正要填的评论表单控件错位**，导致识别“看起来对”但填错或填不到评论区（例如 Spletišče 在评论 form 里，但索引对到别的 form）。

2. **多语言仅靠关键词，未覆盖小语种**  
   - 评论表单的兜底是 **recognizeCommentByKeywords**，依赖 `COMMENT_FIELD_KEYWORDS`（如 comment、commentName、commentEmail、commentWebsite 的 name/label/placeholder 英文 + 少量中文）。
   - 像斯洛文尼亚语 “Spletišče”（网站）、 “Ime”/“E-pošta”/“Komentar” 等若未加入关键词列表，规则匹配就会漏掉。
   - 每增加一种语言就要改规则，难以维护。

3. **AI 识别时若用了 formHtml**  
   - 当前 `buildCommentFormAIPrompt` 在存在 `formMetadata.formHtml` 时会把这段 HTML 发给 AI，且说明 “fieldIndex 按 HTML 中 input/textarea/select 出现顺序”。
   - 但该 HTML 是「第一个 form」的，不是「评论 form」的，所以多 form 页面上 AI 看到的仍不是评论区，多语言再强也无法识别到 “Spletišče”。

结论：**多语言漏识别（如 Spletišče）既来自“规则未适配”，也来自“评论表单未单独圈定、formHtml 与 fields 可能不对应评论区”。**

### 1.3 小结：当前局限性

| 问题 | 原因 |
|------|------|
| 多语言字段漏识别（如 Spletišče） | 规则只覆盖有限关键词；且 AI 看到的 HTML 可能不是评论 form |
| 多 form 时识别/填充错位 | formHtml = 第一个 form，fields = 所有 form 拼接，fieldIndex 与评论 form 不对应 |
| 每次新语言要改规则 | 关键词列表维护成本高 |
| 两次请求 | 先 aiRecognizeCommentForm，再 generateBlogComment，延迟与成本双倍 |

## 二、目标：一发请求同时完成「元素定位 + 评论生成」

- **输入**：评论区域（或评论 form）的 **HTML** + 页面 **title** + **description**。
- **一次 LLM 请求** 返回：
  - **mappings**：每个可填字段的 fieldIndex → standardField（comment / commentName / commentEmail / commentWebsite）；
  - **submitButtonFieldIndex**：提交按钮在“同一字段列表”中的索引；
  - **comment**：根据 title/description 生成的约 200 字评论正文。
- **Content 侧**：用同一套 **仅针对评论 form** 的 `fields` 列表，按 fieldIndex 从 `formMetadata.fields[fieldIndex]` 取 locator，执行填充并点提交。

这样：

- 多语言由 AI 直接读评论区 HTML 理解（如 Spletišče → commentWebsite），无需扩展规则。
- 只要 **评论 form 的 HTML 与构建 fields 的 form 一致**，fieldIndex 就与 DOM 一一对应，不会错位。
- 一次请求即可拿到「定位 + 评论」，延迟与 token 更优。

## 三、可行性评估（基于当前项目）

- **Background 已有能力**：  
  - 已有 `handleAIRecognizeCommentForm`、`handleGenerateBlogComment`，以及 `fetchLlmWithRetry`、LLM 配置读取、JSON 解析（含 reasoning 兼容）。  
  - 合并为「一发」只需新增一个 handler，在一次请求里完成：  
    - 用「评论 form HTML + title + description」拼一个统一 prompt；  
    - 约定返回 JSON：`{ mappings, submitButtonFieldIndex, comment }`；  
    - 解析后仍用现有 `formMetadata.fields` 把 fieldIndex 转成 locator（见下）。
- **Content 已有能力**：  
  - 已有 `getCommentFormMetadata()`、`findElementByLocator`、`fillCommentForm`、评论缓存与状态。  
  - 需要改动的点：  
    1）**只针对“评论 form”** 生成 formMetadata（见下「评论 form 的圈定」）；  
    2）一次发 `blogCommentOneShot`（formMetadata + title + description），用返回的 mappings + submitButton + comment 直接填充，不再分别调 `aiRecognizeCommentForm` 和 `generateBlogComment`。
- **定位仍用现有 locator 体系**：  
  - AI 只返回 fieldIndex（和 submitButtonFieldIndex），不返回 selector/XPath。  
  - Content 保证 **formMetadata.fields 与发给 AI 的 HTML 来自同一个 form**，且顺序一致，则 `formMetadata.fields[fieldIndex]` 的 locator 即可用于 `findElementByLocator`，无需改 background 或解析逻辑。

结论：**在当前架构下，一发请求同时返回「元素定位 + 评论」完全可行**，且能直接缓解多语言与多 form 错位问题。

## 四、实现方案（明确步骤）

### 4.1 评论 form 的圈定（Content）

目标：**只对“评论提交区”的 form 取 HTML 和 fields**，保证发给 AI 的 HTML 与 fields 一一对应。

- **实现位置**：formHandler.js，新增 `getCommentFormElement()`（或等价函数），返回「最可能是评论表单」的 `<form>` 元素；若无则 `null`。
- **推荐策略**（可组合，按优先级）：
  1. **DOM 结构 + 文案**：  
     遍历 `document.querySelectorAll('form')`，对每个 form 取：
     - 其自身或祖先（如父级 div）的文本中是否包含评论/回复类关键词（如 comment、reply、komentar、odgovor、评论、回复、留言、DODAJ ODGOVOR 等）；
     - 且该 form 内是否存在 **textarea**（评论正文通常为多行）。
  2. **若存在多个带 textarea 的 form**：  
     取其中「textarea 体积最大」或「label/placeholder 最像评论+姓名+邮箱+网站」的那一个。
  3. **兜底**：若仍无法判定，可保留「最后一个 form」或「第一个包含 textarea 的 form」，并加注释说明。
- **getCommentFormMetadata() 改造**：
  - 先调用 `getCommentFormElement()` 得到 `commentForm`。
  - 若 `commentForm` 存在：
    - **fields**：仅从 `commentForm` 内用现有逻辑收集 `input/textarea/select`（排除 hidden/submit/button/reset），再追加该 form 内的 submit/button，**不再**合并其他 form。
    - **formHtml**：`commentForm.outerHTML.slice(0, 12000)`（或略大，按 token 预算）。
  - 若 `commentForm` 为 null：退化为当前行为（所有 form 的 fields + 第一个 form 的 formHtml），保证兼容。

这样，**发给 AI 的 HTML 与 formMetadata.fields 严格对应同一个 form**，fieldIndex 即该 form 内控件的顺序。

### 4.2 一发请求的 Background 逻辑

- **新 action 名**：例如 `blogCommentOneShot`。
- **入参**：`{ formMetadata, title, description }`。  
  - formMetadata 必须包含：`fields`（与 formHtml 同源）、`formHtml`（评论 form 的 HTML）。
- **Prompt 设计**（要点）：
  - 说明：给定一段 **博客评论表单的 HTML** 以及页面 **标题和描述**，请完成两件事：  
    (1) 识别表单中每个可填字段（input/textarea），按在 HTML 中出现的顺序从 0 编号，并映射到：`comment`（评论文本）、`commentName`（姓名）、`commentEmail`（邮箱）、`commentWebsite`（个人网站 URL）；指出哪个是提交按钮（提交评论/Post comment/Objavi komentar 等）。  
    (2) 根据标题和描述生成一条约 200 字符、自然友好的英文评论。
  - 要求 **仅** 返回一个 JSON 对象，且不要 markdown 包裹，例如：  
    `{ "mappings": [ {"fieldIndex": 0, "standardField": "comment"}, ... ], "submitButtonFieldIndex": 4, "comment": "Generated comment text here." }`  
  - 约定：fieldIndex 与 HTML 中 input/textarea 出现顺序一致；提交按钮若在表单内且可识别，则为其在「同一顺序」中的索引，否则 -1。
- **一次 LLM 调用**：使用现有 endpoint、apiKey、fetchLlmWithRetry；可适当提高 max_tokens（如 2048）以容纳 mappings + 长评论。
- **解析**：
  - 从返回中抽取 JSON（兼容 content 为空、从 reasoning 里取等，与现有 parse 逻辑一致）。
  - 得到 `mappings`、`submitButtonFieldIndex`、`comment`。
  - 用现有 `formMetadata.fields` 将 fieldIndex 转为带 locator 的 mapping 项（与 `parseCommentFormAIResponse` 相同方式），并得到 submitButton 的 locator（若 submitButtonFieldIndex >= 0 且对应项为按钮）。
- **返回值**：`{ mappings, submitButton, comment }`，与现有 `handleAIRecognizeCommentForm` 的返回形状兼容（仅多一个 comment 字段）。

### 4.3 Content 侧调用与流程

- **入口**：在「生成评论并填充」流程中（例如 popup 触发后 Content 执行的逻辑）：
  1. 调用改造后的 `getCommentFormMetadata()`，得到 **仅评论 form** 的 formMetadata（含 formHtml + fields）。
  2. 若 `!formMetadata.hasForm || !formMetadata.fields?.length`，直接报错「未检测到评论表单」。
  3. 取 `title = document.title`，`description = document.querySelector('meta[name="description"]')?.content ?? ''`。
  4. 发一条消息：`chrome.runtime.sendMessage({ action: 'blogCommentOneShot', formMetadata, title, description })`。
  5. 收到 `{ mappings, submitButton, comment }` 后：
     - 写回 comment 表单状态（如 commentFormState.fieldMappings = mappings, commentFormState.submitButton = submitButton）；
     - 可选：按当前策略写缓存（blogCommentFieldMappings），以便下次同页可只用缓存不请求（此时评论仍可用缓存或再生成）；
     - 调用现有 `fillCommentForm(siteId, comment)`，传入 AI 返回的 `comment`，其余 name/email/website 仍从站点档案取；
     - 若无防 spam 验证则按现有逻辑点击提交。
- **不再** 单独调用 `generateBlogComment` 或先 `aiRecognizeCommentForm` 再生成评论；一次 `blogCommentOneShot` 替代两者。

### 4.4 兼容与降级

- **未配置 LLM 或 OneShot 失败**：  
  - 可回退为：先 `recognizeCommentForm(useLlm: false)`（仅关键词），再单独 `generateBlogComment`（若之前实现过）；或仅填充不生成评论（comment 留空由用户手填）。  
  - 建议在 Content 或 Popup 提示：「未配置 AI 或请求失败，已用规则识别；评论内容请手动填写。」
- **缓存**：  
  - 若本次使用 OneShot 成功，可将 `{ mappings, submitButton }` 按现有 cacheKey 写入 blogCommentFieldMappings，下次同页可优先用缓存并只生成评论（或仍走 OneShot 以统一体验）。可选：缓存中增加 `comment` 的生成策略（例如不缓存 comment，每次都生成）。

### 4.5 文件与改动清单

| 位置 | 改动 |
|------|------|
| **content/formHandler.js** | 1）新增 `getCommentFormElement()`，实现评论 form 圈定；2）改造 `getCommentFormMetadata()`，仅基于该 form 生成 fields + formHtml；3）在「生成评论并填充」流程中改为调用 `blogCommentOneShot` 一次，用返回的 mappings + submitButton + comment 填充。 |
| **background.js** | 1）新增 `blogCommentOneShot` 的 message 分支；2）实现 `handleBlogCommentOneShot(formMetadata, title, description)`：拼统一 prompt、一次 fetch、解析 `mappings + submitButtonFieldIndex + comment`、按 formMetadata.fields 转 locator，返回 `{ mappings, submitButton, comment }`。 |
| **popup**（若由 popup 驱动） | 若有「先识别再生成评论」的两步逻辑，改为一次触发「生成评论并填充」，由 Content 内部完成 OneShot 调用与填充，无需改 popup 协议（仅保证传 siteId 等）。 |

## 五、预期效果

- **多语言**：AI 直接根据评论区 HTML 中的标签（如 Spletišče、Ime、E-pošta、Komentar）映射到 standardField，无需再维护多语言关键词。
- **多 form**：评论 form 单独圈定后，HTML 与 fields 一致，fieldIndex 准确对应评论区控件，不再错位。
- **成本与延迟**：一次请求同时拿到「元素定位 + 评论」，减少一次 round-trip 和一次 token 消耗。
- **可维护性**：新语言、新站点样式主要依赖 AI 理解 HTML，规则仅作兜底，减少规则适配。

按上述方案实现后，再配合需求书中的「提交后验证」（重新读页、查找可点本站链接），即可形成完整的评论提交与验证闭环。
