# 评论识别流程与「一发请求」实现方案（简化版）

## 一、需求目标（唯一聚焦点）

**在没有缓存的前提下，当前会发起两次 AI 请求：**

| 顺序 | 请求 | 作用 | 典型日志 |
|------|------|------|----------|
| 1 | `generateBlogComment(title, description)` | 根据标题和描述生成约 200 字英文评论 | `[Background][BlogComment] 请求开始` |
| 2 | `aiRecognizeCommentForm(formMetadata)` | 根据表单字段列表/HTML 识别 comment/name/email/website + 提交按钮 | `[AI Form 识别-评论] 请求完整 JSON` |

**目标：将上述两次请求合并为一次请求**，在延迟和 token 成本上均减半，同时保持现有能力（多语言字段识别、评论生成）不变。

---

## 二、当前数据流（无缓存时）

```
Popup 点击「生成评论并填充」
  → getPageMetadata (title, description)
  → Background: generateBlogComment(title, description)     ← 第 1 次 AI
  → Content:  recognizeCommentForm(useLlm: true)
       → getCommentFormMetadata()
       → Background: aiRecognizeCommentForm(formMetadata)   ← 第 2 次 AI
  → Content: fillCommentForm(siteId, genRes.comment)
```

两次请求彼此独立：评论生成不依赖表单结构，表单识别不依赖评论内容。因此可以在一次调用中由模型同时完成两件事。

---

## 三、一发请求：接口约定

### 3.1 新 Action（Background）

- **名称**：`blogCommentOneShot`
- **入参**：`{ formMetadata, title, description }`
  - `formMetadata`：必须包含与「评论 form」对应的 `fields` 与 `formHtml`（保证 fieldIndex 与 fields 一致，见下节）。
  - `title`：`document.title`
  - `description`：`meta[name="description"]?.content`

### 3.2 一次 LLM 请求的 Prompt 要求

模型需要同时完成两件事：

1. **表单字段映射**：按给定表单字段列表（或 HTML 中 input/textarea 顺序）从 0 编号，映射到 `comment` / `commentName` / `commentEmail` / `commentWebsite`，并指出提交按钮的 `submitButtonFieldIndex`（无则为 -1）。
2. **评论生成**：根据 title 和 description 生成一条约 200 字符、自然友好的英文评论。

### 3.3 返回格式（仅 JSON，无 markdown）

要求模型**只**返回一个 JSON 对象，且不要用 markdown 代码块包裹，例如：

```json
{
  "mappings": [
    { "fieldIndex": 0, "standardField": "comment" },
    { "fieldIndex": 1, "standardField": "commentName" },
    ...
  ],
  "submitButtonFieldIndex": 8,
  "comment": "Generated comment text here."
}
```

- `fieldIndex` 与发给 AI 的 `formMetadata.fields` 下标一致。
- `submitButtonFieldIndex` 为同一列表中的提交按钮索引，未找到则为 -1。
- `comment` 为最终要填入评论框的正文。

### 3.4 Background 解析与返回

- 从 LLM 返回中解析出 `mappings`、`submitButtonFieldIndex`、`comment`（沿用现有 JSON 抽取逻辑，兼容 markdown 包裹）。
- 用现有 `formMetadata.fields` 将 `fieldIndex` 转为带 `locator` 的 mapping 项，并得到 `submitButton` 的 locator（与当前 `parseCommentFormAIResponse` 一致）。
- **返回给 Content/Popup**：`{ success: true, result: { mappings, submitButton, comment } }`，与现有识别接口兼容，仅多一个 `comment` 字段。

## 四、调用流程（一发替代两发）

### 4.1 评论 form 与 formMetadata（重要前提）

为保证 `fieldIndex` 与 DOM 一一对应，**发给 AI 的 HTML 与 fields 必须来自同一个「评论 form」**：

- 在 Content 中：先通过 `getCommentFormElement()`（或等价逻辑）确定「评论表单」对应的 `<form>`，再仅针对该 form 生成 `fields` 和 `formHtml`。
- 若暂无圈定逻辑，则至少保证 `formMetadata.formHtml` 与 `formMetadata.fields` 对应同一 form（例如仅取「第一个 form」或「第一个含 textarea 的 form」），避免多 form 时错位。

（评论 form 圈定的具体策略见原文档「4.1 评论 form 的圈定」。）

### 4.2 Popup / Content 侧流程（无缓存时）

1. 取 `formMetadata = getCommentFormMetadata()`（仅评论 form）、`title`、`description`。
2. 若 `!formMetadata.hasForm || !formMetadata.fields?.length`，直接报错「未检测到评论表单」。
3. 发一条消息：`chrome.runtime.sendMessage({ action: 'blogCommentOneShot', formMetadata, title, description })`。
4. 收到 `{ success: true, result: { mappings, submitButton, comment } }` 后：
   - 写回 Content 状态：`commentFormState.fieldMappings = mappings`，`commentFormState.submitButton = submitButton`；
   - 可选：按现有策略写缓存（如 `blogCommentFieldMappings`），key 仍用当前 cacheKey；
   - 调用现有 `fillCommentForm(siteId, comment)`，传入 OneShot 返回的 `comment`，其余 name/email/website 从站点档案取；
   - 若无防 spam 验证则按现有逻辑点击提交。

**不再**单独调用 `generateBlogComment` 或先 `aiRecognizeCommentForm` 再生成评论；一次 `blogCommentOneShot` 替代两者。

### 4.3 有缓存时的行为（已确认）

**当前实现（与一发方案无关）：有缓存时只会发一次 AI 请求 —— 即「AI 评论生成」。**

- Popup 始终先调 `generateBlogComment(title, description)`（1 次 AI）。
- 再调 Content 的 `recognizeCommentForm(useLlm: true)`；Content 内会先查缓存，若命中则**直接返回缓存的 mappings/submitButton**，不会调用 `aiRecognizeCommentForm`，因此**不会发第二次 AI 请求**。
- 结论：有缓存 = 仅 1 次 AI（评论生成）；无缓存 = 2 次 AI（评论生成 + 表单识别）。一发方案要解决的是「无缓存时的 2 次 → 1 次」。

### 4.4 一发实现后的缓存策略（可选）

- 若本次使用 OneShot 成功，可将 `{ mappings, submitButton }` 按现有 cacheKey 写入，下次同页可**仅用缓存做字段定位**，评论可：
  - 再发一次仅生成评论的请求（保留现有 `generateBlogComment` 作降级），或
  - 仍走 OneShot（统一体验，多一次评论生成 token）。
- 建议：**有缓存时**保持现有逻辑——只调 `recognizeCommentForm`（命中缓存） + `generateBlogComment`，即只进行 AI 评论生成；无缓存时走 OneShot，一次拿到 mappings + submitButton + comment。

## 五、文件与改动清单

| 位置 | 改动 |
|------|------|
| **background.js** | 1）新增 `blogCommentOneShot` 的 message 分支；2）实现 `handleBlogCommentOneShot(formMetadata, title, description)`：拼统一 prompt（字段映射 + 评论生成）、一次 fetch、解析 `mappings + submitButtonFieldIndex + comment`、用 `formMetadata.fields` 转 locator，返回 `{ mappings, submitButton, comment }`。 |
| **content/formHandler.js** | 1）评论 form 圈定（`getCommentFormElement()`）与 `getCommentFormMetadata()` 仅基于该 form；2）在「生成评论并填充」流程中，无缓存时改为调用 `blogCommentOneShot` 一次，用返回的 mappings + submitButton + comment 填充，不再分别调 `aiRecognizeCommentForm` 和 `generateBlogComment`。 |
| **popup/popup.js** | 无缓存时：不再先 `generateBlogComment` 再 `recognizeCommentForm`；改为由 Content 主导一次 `blogCommentOneShot`（或 Popup 先取 formMetadata + title + description 后直接发 `blogCommentOneShot`，再通知 Content 填充），具体取决于当前是由 Popup 还是 Content 发起 AI 调用。 |

## 六、预期效果

- **延迟与成本**：无缓存时从 2 次 AI 请求变为 1 次，round-trip 与 token 均减半。
- **能力不变**：多语言字段识别、评论生成质量与现有行为一致，仅合并为一次调用。
- **兼容**：返回形状与现有 `handleAIRecognizeCommentForm` 一致并多出 `comment`，Content 填充逻辑可复用。

实现完成后，无缓存场景下后台仅会出现**一次** `[BlogComment OneShot]` 类请求日志，不再分别出现「评论生成」与「AI Form 识别-评论」两次请求。
