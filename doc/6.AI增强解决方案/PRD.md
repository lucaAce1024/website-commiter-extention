# PRD — AI 增强评论提交系统 v2.1

> 产品需求文档 | 版本 2.1 | 2026-03-09

---

## 1. 背景与目标

### 1.1 当前痛点


| #   | 问题                               | 影响                  | 严重度  |
| --- | -------------------------------- | ------------------- | ---- |
| P1  | Cookie/隐私弹窗遮挡表单，标准流程和批量模式无法处理    | 大量页面直接返回"找不到form表单" | 🔴 高 |
| P2  | 启发式关键词仅覆盖英文+中文，多语言页面匹配全部失败       | 日/德/法/斯/捷等语言页面无法提交  | 🔴 高 |
| P3  | 表单检测强依赖 `<form>` 标签，非标准布局直接判定无表单 | Disqus、自定义组件等场景失败   | 🟡 中 |
| P4  | 流程每一步单轮无状态，失败后无法自修复              | 任何意外都导致整个任务失败       | 🔴 高 |
| P5  | 勾选确认项（checkbox）识别范围有限            | 未勾选必要项导致提交被拒        | 🟡 中 |
| P6  | 已关闭评论的页面仍然尝试识别和调用 LLM            | 批量模式浪费时间和 token     | 🟡 中 |


### 1.2 目标

**一句话**：通过弹窗预处理 + 多语言增强 + 多轮对话 Agent Loop，将评论提交成功率从当前约 40% 提升到 75%+。

**量化指标**：


| 指标                   | 当前         | 目标  |
| -------------------- | ---------- | --- |
| 标准英文 WordPress 表单成功率 | ~70%       | 95% |
| 多语言表单成功率             | ~10%       | 70% |
| 有弹窗页面成功率             | ~0%        | 80% |
| 非标准表单成功率             | ~5%        | 50% |
| 批量模式平均单页耗时           | 15s（含大量失败） | 12s |
| 无评论页面判定耗时            | 30s+（超时）   | <8s |

## 2. 用户场景

### 场景 1：单页评论提交（Side Panel）

用户在 Side Panel 中选择目标站点，点击"生成评论并填充"。系统自动：

1. 关闭页面上的弹窗（如有）
2. 检测评论表单
3. 生成评论内容
4. 填充所有字段（Name/Email/Website/Comment）
5. 勾选必要的 checkbox
6. 点击提交

**增强后变化**：

- 步骤 1 新增弹窗预处理（之前不存在）
- 步骤 2-5 遇到异常时自动进入 Agent Loop 自修复（之前直接失败）

### 场景 2：批量评论提交

用户从飞书同步 URL 列表，点击"开始批量提交"。系统逐个打开 URL 并自动完成评论流程。

**增强后变化**：

- 每个 URL 先走弹窗预处理 + 快速路径
- 快速路径失败时自动进入 Agent Loop
- 无评论表单的页面快速跳过（<8s）
- 不可绕过的障碍（reCAPTCHA）快速终止并标记

### 场景 3：完全 AI 识别模式

用户勾选"完全AI识别"后提交。当前流程保留，但改造为两级架构：

- 快速路径（程序启发式）→ 成功则 0 次 LLM 调用
- Agent Loop（多轮对话自修复）→ 作为 fallback

## 3. 功能需求

### FR-1：弹窗预处理


| 项目       | 说明                                                                           |
| -------- | ---------------------------------------------------------------------------- |
| **描述**   | 在任何评论填充流程开始前，自动检测并关闭页面上的 Cookie/隐私/GDPR 同意弹窗                                 |
| **触发条件** | 页面加载完成后，评论流程启动时自动执行                                                          |
| **处理方式** | 第一级：纯程序选择器 + fixed 元素文本匹配（<500ms） 第二级：Snapshot + LLM 识别按钮（仅第一级无效时触发）         |
| **最大轮次** | 程序级 2 轮 + LLM 级 1 轮                                                          |
| **适用范围** | 标准流程 + 完全AI识别 + 批量模式                                                         |
| **验收标准** | AC-1: 能关闭 CookieConsent、OneTrust、GDPR 类弹窗 AC-2: 不误点击正常页面元素 AC-3: 弹窗处理耗时 < 3s |


### FR-2：表单检测增强


| 项目       | 说明                                                      |
| -------- | ------------------------------------------------------- |
| **描述**   | 当标准 `<form>` 检测失败时，通过 Snapshot 辅助检测评论区是否存在              |
| **新增能力** | 1) Snapshot 搜索 textbox/textarea 节点 2) 快速判定"不可评论"页面并提前终止 |
| **验收标准** | AC-1: 评论区不在 `<form>` 内的页面能被识别 AC-2: 已关闭评论的页面在 8s 内终止    |


### FR-3：多语言元素识别


| 项目       | 说明                                                                                                       |
| -------- | -------------------------------------------------------------------------------------------------------- |
| **描述**   | 扩展启发式匹配的关键词覆盖范围，支持 10+ 种语言                                                                               |
| **覆盖语言** | 英/中/日/德/法/西/葡/意/斯洛文尼亚/捷克/韩/俄                                                                             |
| **增强内容** | 1) 多语言 SLOT_KEYWORDS 2) `<label for>` 关联采集 3) textarea 回退（唯一 textarea = comment） 4) `type="submit"` 直接匹配 |
| **验收标准** | AC-1: 日语/德语/斯洛文尼亚语评论表单 Name/Email/Website/Comment 全部正确匹配 AC-2: 不依赖 LLM 即可完成常见多语言表单                       |


### FR-3.1：全量填充策略（迭代 v2.1）

| 项目       | 说明                                                                 |
| -------- | ------------------------------------------------------------------ |
| **描述**   | 采集表单中**全部**可填充字段，通过 AI 判断每个字段是否需要填充，**尽量填充**所有能填的字段 |
| **典型遗漏场景** | Nickname、Display Name、Author 等非标准命名字段未被识别时导致留空                       |
| **实现方式** | 1) Snapshot 输出所有可交互 input/textarea 2) AI 对每个候选项判断是否属于 name/nickname/email/comment/其他 3) 无明确语义的字段也尝试用昵称/站点名等填充 |
| **验收标准** | AC-1: 含 "Nickname" 的评论表单能自动填充 AC-2: 含 "Author"、"Display Name" 的表单能自动填充 AC-3: 尽量填充，不因字段名称非常规而漏填 |


### FR-4：勾选确认项增强


| 项目       | 说明                                                                                                |
| -------- | ------------------------------------------------------------------------------------------------- |
| **描述**   | 识别并自动勾选提交前必要的 checkbox                                                                            |
| **增强内容** | 1) 扩展 checkbox 关键词 2) 识别 role=switch、aria-checked 等非标准 checkbox 3) "Save my name" 类 checkbox 默认勾选 |
| **验收标准** | AC-1: WordPress "Save my name" checkbox 能自动勾选 AC-2: "Notify me" / "I agree to terms" 能自动勾选        |


### FR-5：多轮对话 Agent Loop


| 项目          | 说明                                                                                                                                |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------- |
| **描述**      | 当程序启发式路径失败时，启动带上下文的多轮 AI Agent Loop 进行自修复                                                                                         |
| **核心机制**    | Observe(Snapshot) → Decide(LLM) → Act(Execute) → Evaluate(Result) 循环                                                              |
| **触发条件**    | 快速路径（程序启发式）执行失败后自动触发                                                                                                              |
| **最大轮次**    | 5 轮                                                                                                                               |
| **上下文管理**   | messages 数组累积历史，保留最近 4 轮完整内容，旧轮自动截断为摘要                                                                                            |
| **AI 输出格式** | `{ thought, actions: [{op, uid, value?, checked?}], status }`                                                                     |
| **终止状态**    | `done`（成功提交）/ `no_form`（无表单）/ `blocked`（不可绕过）                                                                                     |
| **验收标准**    | AC-1: 弹窗→表单→提交的完整流程能在 3 轮内完成 AC-2: element_not_found 后能在下一轮自动修正 AC-3: reCAPTCHA 页面 1 轮终止 AC-4: 总 token 消耗 ≤ 10000/任务 AC-5: 批量模式可用 |


### FR-6：快速路径保留


| 项目       | 说明                                                        |
| -------- | --------------------------------------------------------- |
| **描述**   | 简单表单仍走程序启发式快速路径，不消耗 LLM token                             |
| **流程**   | 弹窗预处理（程序）→ Snapshot → 启发式匹配 → 执行                          |
| **验收标准** | AC-1: 标准 WordPress 评论表单走快速路径，0 次 LLM 调用 AC-2: 快速路径耗时 < 5s |


### FR-7：提交后登录重定向处理（迭代 v2.1）

| 项目       | 说明                                                                                                                                 |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| **描述**   | 点击提交后若页面发生 URL 跳转（如跳转到登录页），则进行二次 Snapshot，从账号密码清单中查找对应站点的凭据完成登录                                                                                  |
| **触发条件** | 提交动作完成后，检测到当前 URL 与初始 URL 不同（或域名下的路径发生变化）                                                                                         |
| **数据来源** | 飞书表格「媒体账号统计」tab 页，文档链接见下方数据源章节                                                                                                         |
| **处理流程** | 1) 检测到跳转 → 二次 takeSnapshot 2) 识别登录表单（Email/密码输入框、Log in 按钮） 3) 从缓存中按域名/URL 查找对应凭据 4) 填充账号密码并点击登录 5) 登录成功后继续原流程（或重新提交评论） |
| **异常处理** | 缓存中找不到对应站点凭据 → 提醒用户「请辅助注册」或「请补充该站点账号到飞书表格」                                                                                                       |
| **验收标准** | AC-1: 提交后跳转登录页时自动二次 Snapshot AC-2: 能正确识别 Email/Password 字段并填充 AC-3: 找到凭据时自动登录并继续 AC-4: 找不到凭据时明确提醒用户 |

#### FR-7 附：凭据缓存数据源与结构

**飞书电子表格**：<https://my.feishu.cn/sheets/FgWhsDQdNhWfVot4787ceNMXnDd>  
**工作表名称**：媒体账号统计

**表格字段定义**：

| 列名     | 说明                                  | 示例                              |
| ------ | ----------------------------------- | ------------------------------- |
| 平台     | 站点/平台名称（用于人工辨识）                     | `gamedev`                       |
| 账号名    | 登录用户名（部分站点使用）                       | `luna123`                       |
| 登录密码   | 登录密码                                | `%Dxf18710360436`               |
| 登录邮箱   | 登录邮箱（大部分站点用邮箱+密码登录）                 | `l21210896@gmail.com`           |
| 网址     | 站点首页 URL（用于域名匹配）                    | `https://gamedev.net/`          |

**Chrome Extension 内部存储结构**（`chrome.storage.local`）：

```typescript
interface SiteCredential {
  platform: string;      // 平台名称
  username: string;      // 账号名
  password: string;      // 登录密码
  email: string;         // 登录邮箱
  url: string;           // 网址（原始值）
  domain: string;        // 从 url 提取的域名，用于快速匹配
}

// 存储 key: 'siteCredentials'
// 存储格式: SiteCredential[]
```

**域名匹配规则**：

1. 从当前页面 URL 提取域名（如 `www.gamedev.net` → `gamedev.net`）
2. 在 `siteCredentials` 中查找 `domain` 匹配的记录
3. 匹配优先级：精确匹配 > 后缀匹配（`xxx.gamedev.net` 匹配 `gamedev.net`）
4. 找到多条时取第一条

**登录表单填充规则**：

1. 如果登录表单有 Email 字段 → 填充 `email`
2. 如果登录表单有 Username 字段 → 填充 `username`
3. 如果表单同时有 Email 和 Username → 优先填 `email`
4. Password 字段 → 填充 `password`

**数据同步方式：飞书 Sheets API 直接读取**

通过飞书自建应用的 `tenant_access_token` 调用电子表格 Sheets API 读取「媒体账号统计」工作表数据，同步到 Chrome Extension 本地存储。

**飞书 API 调用链路**：

```
┌─────────────────────────────────────────────────────────────────────┐
│ 1. 获取 tenant_access_token                                         │
│    POST https://open.feishu.cn/open-apis/auth/v3/tenant_access_token/internal/
│    Body: { app_id, app_secret }                                     │
│    → 返回 tenant_access_token（有效期 2h）                            │
├─────────────────────────────────────────────────────────────────────┤
│ 2. 查询工作表列表                                                    │
│    GET /sheets/v3/spreadsheets/{spreadsheetToken}/sheets/query       │
│    → 按名称找到「媒体账号统计」的 sheet_id + 行数                       │
├─────────────────────────────────────────────────────────────────────┤
│ 3. 读取工作表全部数据                                                 │
│    GET /sheets/v2/spreadsheets/{spreadsheetToken}/values/{sheetId}!A1:Z{rowCount}
│    → 返回 values[][]（二维数组：首行表头，后续行为数据）                  │
├─────────────────────────────────────────────────────────────────────┤
│ 4. 解析表头列名→字段映射，逐行转为 SiteCredential                      │
│    → 写入 chrome.storage.local('siteCredentials')                    │
└─────────────────────────────────────────────────────────────────────┘
```

**鉴权配置**：复用 Options 页「飞书配置」tab 已有的 App ID / App Secret，无需重复配置。

在同一 tab 下的「发外链登录账号」区域额外配置：

| 配置项                | 说明                                                          | 存储 key（credConfig）               |
| ------------------ | ----------------------------------------------------------- | --------------------------------- |
| 电子表格 Token         | 从表格链接提取（默认预填 `FgWhsDQdNhWfVot4787ceNMXnDd`）                 | `credConfig.spreadsheetToken`     |
| 工作表名称              | 默认预填「媒体账号统计」，支持修改                                            | `credConfig.sheetName`            |

> App ID / App Secret 存储在 `feishuConfig` 中，密码类型输入框不以明文展示。

**同步时机**：

1. **Options 页手动同步**：点击「从飞书同步」按钮 → 立即拉取 → 显示同步结果（成功 N 条 / 失败原因）
2. **批量任务启动前自动同步**：每次开始批量提交前自动拉取最新数据
3. **token 缓存**：`tenant_access_token` 有效期 2h，可复用

**飞书应用权限要求**：

- `sheets:spreadsheet:readonly` — 读取电子表格数据

**错误处理**：

| 错误场景                   | 处理方式                                        |
| ---------------------- | ------------------------------------------- |
| App ID/Secret 未配置       | Options 页提示「请先配置飞书应用凭证」                      |
| token 获取失败（401/403）     | 提示「飞书凭证无效或权限不足，请检查 App ID/Secret 和应用权限」       |
| Wiki Token 无效           | 提示「飞书文档链接无效，请检查 Wiki Token」                   |
| Table 名称未找到             | 提示「未找到名为 XXX 的 Tab 页」                        |
| 网络超时                    | 重试 1 次，仍失败则提示「网络异常，请稍后重试」                    |


### FR-8：验证环节优化（迭代 v2.1）

| 项目       | 说明                                                                         |
| -------- | -------------------------------------------------------------------------- |
| **描述**   | 提交后验证评论是否成功时，应从**页面底部向上**查找，因为新提交的评论通常出现在列表底部，历史已提交的评论可能在上方                             |
| **实现方式** | verifyCommentSubmission 等验证逻辑改为：优先从评论区容器底部开始扫描，或按时间倒序查找（新评论在前） |
| **验收标准** | AC-1: 含多条历史评论的页面，能正确识别刚提交的那条（通常在底部） AC-2: 不误判为"未找到" |


### FR-9：完成判定标准（迭代 v2.1）

| 项目       | 说明                                                             |
| -------- | -------------------------------------------------------------- |
| **描述**   | **不到最后验证提交成功，不算作完成一个完整流程**                                              |
| **判定时机** | 必须在 verifyCommentSubmission（或等价验证逻辑）确认站点链接/评论内容出现在页面上后，才标记任务为 success |
| **不视为完成** | 仅"点击了提交按钮"或"执行了填充动作"但未验证到提交结果，不能算完成                                   |
| **验收标准** | AC-1: 批量模式中 success 仅在实际验证到评论成功时标记 AC-2: 验证失败的任务标记为失败，不误报成功 |

## 4. 非功能需求

### NFR-1：性能


| 场景               | 目标耗时  | LLM 调用       |
| ---------------- | ----- | ------------ |
| 简单表单（快速路径）       | < 5s  | 0（仅评论生成 1 次） |
| 有弹窗 + 标准表单       | < 10s | 0-1          |
| 复杂表单（Agent Loop） | < 30s | 2-4 轮        |
| 无评论表单页面          | < 8s  | 0-1          |
| 遇到 reCAPTCHA     | < 10s | 0-1          |


### NFR-2：成本

- 单次任务 token 预算：≤ 10000 tokens（Agent Loop 路径）
- 快速路径 token 消耗：0（仅评论生成消耗 ~500 tokens，不在本次统计范围）
- 批量 100 个 URL 总 token：约 200k-500k tokens（取决于失败率）

### NFR-3：兼容性

- 所有增强不改变现有消息协议（`chrome.runtime.onMessage` 接口不变）
- 现有缓存/关键词/AI OneShot 路径正常工作，不受影响
- Side Panel UI 无需改动（操作由 background → content 驱动）

### NFR-4：可观测性

- Agent Loop 每轮的 `thought`、`actions`、执行结果输出到控制台日志
- 批量模式每个 URL 的结果（成功/失败原因/轮次数/耗时）记录到任务结果

## 6. 不做什么（Out of Scope）


| 项目                                  | 原因                     |
| ----------------------------------- | ---------------------- |
