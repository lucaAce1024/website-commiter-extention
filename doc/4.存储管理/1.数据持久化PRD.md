## 2. 背景与目标

### 2.1 背景

- 当前扩展对「每个网站（按 hostname + pathname）的评论表单字段定位信息」有缓存逻辑：识别结果会写入 `chrome.storage.local` 的 `blogCommentFieldMappings`，以便同页再次打开时直接使用，避免重复调用 AI。
- 该缓存目前存在以下不足：
  - **备份未覆盖**：创建备份时未包含 `blogCommentFieldMappings`，用户无法在备份文件中保留各站点的字段定位信息。
  - **加载策略未显式区分「缓存」与「持久化」**：未明确「下次打开时若无缓存则从持久化存储加载」的流程，以及缓存与持久化不一致时的处理规则。

### 2.2 目标

1. **持久化存储**：将每个网站缓存的字段定位信息以持久化形式存储在浏览器中（继续使用 `chrome.storage.local`，保证关闭浏览器/重启后仍存在）。
2. **加载策略**：下次打开某页面时，若当前没有可用的缓存，但存在该页对应的持久化数据，则从持久化数据中加载并使用。
3. **备份与恢复**：用户执行「备份」时，将上述持久化数据一并输出到备份文件中；恢复备份时，可正确写回并参与后续的「缓存 vs 持久化」一致性逻辑。
4. **一致性规则**：当同一站点（同一 cacheKey）在「缓存」与「持久化」中存在不一致时，以**时间新旧**为准，**新的覆盖旧的**；若缓存较新，则用缓存覆盖持久化中的该条记录。

## 3. 名词说明

| 名词 | 说明 |
|------|------|
| **字段定位信息** | 单条记录包含：`mappings`（字段映射数组）、`submitButton`（提交按钮定位）、`consentCheckboxes`（可选，同意条款等勾选项定位）、以及时间戳 `cachedAt`。 |
| **cacheKey** | 站点维度的唯一键，当前实现为 `blog_${hostname}${pathname}`，例如 `blog_example.com/blog/post-1`。 |
| **缓存（Cache）** | 运行时读写的那份「评论字段定位」数据；在实现上对应 `chrome.storage.local` 中的键 `blogCommentFieldMappings`（或与持久化共用同一键，见 4.2）。 |
| **持久化（Persistent）** | 期望在浏览器重启、扩展重载后仍然存在的那份「评论字段定位」数据；本方案中与「缓存」共用同一存储键，通过时间戳与写策略保证一致性。 |
| **备份文件** | 用户在选项页/扩展内触发的「备份」操作所生成的 JSON 文件；需包含评论字段定位的持久化数据，以便恢复时写回。 |

## 4. 数据模型

### 4.1 单条记录结构

每个 `cacheKey` 对应一条记录，建议结构为：

```ts
interface BlogCommentFieldMappingEntry {
  mappings: Array<{ locator: object; standardField: string; xpath?: string; ... }>;
  submitButton: { locator: object; xpath?: string; locatorDesc?: string } | null;
  consentCheckboxes: Array<{ locator: object }> | null;
  cachedAt: string;  // ISO 8601，用于新旧比较与一致性判断
}
```

- 现有 content 与 background 已使用类似结构；持久化时需保留 `cachedAt`，且每次写入时更新为当前时间。

### 4.2 存储键与「缓存 / 持久化」关系

- **方案**：不引入第二个存储键，**缓存与持久化共用同一键** `blogCommentFieldMappings`。
- **原因**：  
  - 数据本身已在 `chrome.storage.local`，已具备持久化能力。  
  - 只需在「读」时贯彻「无缓存则从持久化加载」的逻辑（即始终从该键读），在「写」时保证带 `cachedAt` 且写入该键；备份/恢复时对该键做导出与导入即可。  
- **一致性**：若未来出现「内存/会话级缓存」与「该键」两份数据，则按 5.3 节规则以时间戳为准，新覆盖旧，并以新值写回该键（即缓存覆盖持久化）。

## 5. 功能需求

### 5.1 持久化存储

- **FR-1**：每次识别到评论表单并得到字段定位结果（或用户清除后重新识别）后，将结果按 `cacheKey` 写入 `chrome.storage.local` 的 `blogCommentFieldMappings`，且每条记录必须包含 `cachedAt`（写入时为当前时间 ISO 字符串）。
- **FR-2**：写入后，该数据即视为「持久化」数据，在未清除存储、未恢复旧备份覆盖的前提下，浏览器重启或扩展重载后仍可读回。

### 5.2 下次打开时的加载策略

- **FR-3**：当用户再次打开某个页面（或在该页刷新）时，若需要评论字段定位信息（例如进入 Blog 评论流程、或读取缓存用于高亮/填充）：
  - 先按当前页的 `cacheKey` 读取「缓存」——即从 `blogCommentFieldMappings[cacheKey]` 读取。
  - 若该 key 下**没有**有效记录（null / 不存在 / 数据无效），则**不**再区分「缓存」与「持久化」；当前实现下该键即持久化存储，因此「无缓存」等价于「该站点无持久化数据」。
  - 若**有**有效记录，则直接使用该记录（即视为「从持久化加载」），无需额外「从持久化再加载」的步骤。
- **FR-4**：若产品后续引入「会话级缓存」（例如仅内存、不写 storage），则加载顺序为：  
  1）先查会话缓存；  
  2）若缺失，再从 `blogCommentFieldMappings`（持久化）读取；  
  3）若命中，则使用该数据，并可选择写回会话缓存。  
  当前若无会话缓存，则仅需保证「始终从 `blogCommentFieldMappings` 读取」即可满足「没有缓存则从持久化加载」。

### 5.3 缓存与持久化不一致时的处理规则

- **FR-5**：对同一 `cacheKey`，若存在两份可比较的数据（例如：内存/会话中的「缓存」与 storage 中的「持久化」），则根据时间戳 `cachedAt` 比较新旧：
  - **以新的为准**：采用 `cachedAt` 较晚的那条作为真相源。
  - **若缓存较新**：使用缓存内容**覆盖**该 `cacheKey` 在持久化中的记录（即写回 `blogCommentFieldMappings[cacheKey]`）。
  - **若持久化较新**：使用持久化数据；若存在会话缓存，则用持久化数据覆盖会话缓存。
- **FR-6**：每次写入（无论是新识别结果还是「用缓存覆盖持久化」）时，必须更新该条记录的 `cachedAt` 为当前时间，以保证后续比较与一致性。

### 5.4 备份与恢复

- **FR-7**：用户触发「备份」时，备份文件中除现有内容外，必须包含**评论字段定位的持久化数据**：
  - 建议以键名 `blogCommentFieldMappings` 输出到备份 JSON 的 `data` 下（与 `chrome.storage.local` 键名一致，便于恢复时一一对应）。
  - 内容为完整对象：`{ [cacheKey]: BlogCommentFieldMappingEntry, ... }`，且每条含 `cachedAt`。
- **FR-8**：用户执行「从备份恢复」时：
  - **全量替换模式**：若备份中有 `blogCommentFieldMappings`，则用其完整替换当前 storage 中的 `blogCommentFieldMappings`（或按现有「替换」语义：整份 `data` 写回 storage）。
  - **合并模式**：若备份中有 `blogCommentFieldMappings`，应与当前 storage 中同键数据按 **FR-5** 规则合并：同一 `cacheKey` 以 `cachedAt` 新的为准；若备份中的更新则用备份覆盖，若当前更新则保留当前；合并结果写回 `blogCommentFieldMappings`。

## 6. 非功能需求与约束

- **NF-1**：持久化与一致性逻辑不得破坏现有「评论识别 → 写缓存 → 同页再次使用」的流程。
- **NF-2**：备份文件格式需与现有备份版本/结构兼容，仅增加 `blogCommentFieldMappings` 字段；旧备份文件（无该字段）恢复时，不应报错，仅不恢复评论字段定位数据即可。
- **NF-3**：所有时间比较均使用 `cachedAt` 的字符串比较（ISO 8601 可排序），或解析为 Date 后比较，确保「新」的定义一致。

## 7. 实现要点摘要

| 模块 | 要点 |
|------|------|
| **Content / 使用方** | 保持通过 `getCachedCommentMapping(cacheKey)` 读、`cacheCommentMapping(cacheKey, payload)` 写；保证 payload 含 `cachedAt`（写时由调用方或 storage 层统一写入当前时间）。 |
| **Storage** | 若当前由 content 直接写 `chrome.storage.local`，可保持不变；也可统一经 `lib/storage.js` 的 `saveBlogCommentFieldMapping` / `getBlogCommentFieldMapping`，并确保读写都带 `cachedAt`。 |
| **Backup 创建** | 在 `createBackup`（如 `lib/backupService.js`）中，从 `storage.get(null)` 或等价方式取得 `blogCommentFieldMappings`，写入 `backupData.data.blogCommentFieldMappings`。 |
| **Backup 恢复** | 在 `restoreBackupReplace` 中，`backupData.data` 已整体 `storage.set(backupData.data)` 时，确保 `backupData.data` 含 `blogCommentFieldMappings`；在 `restoreBackupMerge` 中，对 `blogCommentFieldMappings` 按 `cacheKey` + `cachedAt` 做合并（新覆盖旧），再写回。 |
| **一致性** | 若引入会话缓存：在读取路径上实现 FR-4；在写入或定时同步时，若发现缓存比持久化新，则执行「用缓存覆盖持久化」并更新 `cachedAt`。 |

## 8. 验收标准

- [ ] 某站点识别评论表单并写入后，关闭浏览器再打开该页，仍能命中缓存（从持久化加载），无需重新识别。
- [ ] 执行一次「备份」，打开备份 JSON，存在 `data.blogCommentFieldMappings`，且内含至少一条带 `cachedAt` 的记录。
- [ ] 恢复该备份（替换或合并）后，storage 中 `blogCommentFieldMappings` 与备份中一致（或按合并规则正确合并）；再次打开对应页面时，仍能使用已恢复的字段定位。
- [ ] 若同一 cacheKey 在缓存与持久化中时间戳不同：采用较新的一条作为结果，且在「缓存更新」场景下，持久化被更新为缓存内容。

## 9. 可行性结论

经与当前代码核对，**上述需求均可实现**，无技术障碍：

| 需求 | 可行性 | 说明 |
|------|--------|------|
| **持久化存储（FR-1/2）** | ✅ 已部分满足 | `content/formHandler.js` 中 `cacheCommentMapping` 已写入 `chrome.storage.local.blogCommentFieldMappings`，且已带 `cachedAt`；无需改存储介质。 |
| **下次打开从持久化加载（FR-3/4）** | ✅ 已满足 | `getCachedCommentMapping` 始终从该键读取，无内存缓存时「无缓存则从持久化加载」即当前行为；若后续加会话缓存，只需在读路径上先查会话再查 storage。 |
| **缓存与持久化一致性（FR-5/6）** | ✅ 可行 | 当前仅一份数据（storage）；若引入会话缓存，在读写/同步处按 `cachedAt` 比较并写回即可。 |
| **备份包含评论字段定位（FR-7）** | ✅ 小改即可 | `lib/backupService.js` 的 `createBackup` 使用 `storage.get(null)` 已能拿到 `blogCommentFieldMappings`，只需在组装 `backupData.data` 时增加 `blogCommentFieldMappings` 的赋值。 |
| **恢复时写回与合并（FR-8）** | ✅ 可行 | 替换模式：`storage.set(backupData.data)` 已会写回 data 中所有键，备份含该键即会恢复。合并模式：在 `restoreBackupMerge` 中增加对 `blogCommentFieldMappings` 按 cacheKey + `cachedAt` 的合并逻辑即可。 |
| **旧备份兼容（NF-2）** | ✅ 自然满足 | `chrome.storage.local.set` 仅更新传入的键；旧备份无 `blogCommentFieldMappings` 时不会误删现有该键，仅不恢复该项。 |

**结论**：按 PRD 第 7 节实现要点实施即可落地，无需变更存储架构或引入新依赖。
